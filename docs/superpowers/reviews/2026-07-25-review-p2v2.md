# Review - P2 v2 (Teacher Attendance, Visitors & Roster)

Plan: `docs/superpowers/plans/2026-07-25-launch-p2-teacher-visitors-roster-v2.md`
Spec: `docs/superpowers/specs/2026-07-24-aug-3-launch-batch-design.md` §4, §5, §6
Prior review (v1): `docs/superpowers/reviews/2026-07-25-review-p2.md`
Baseline: `main` @ `b1395e0`

## Verdict

**REQUEST CHANGES** - 1 critical, 16 major, 14 minor.

v2 fixed almost every v1 finding, and the date helper is now mathematically correct
(verified by execution across Sunday / Monday / Saturday and both 2026 DST switches).
The remaining problems are concentrated in three places:

1. **Task 3's read budget rests on a false premise.** The fid set the plan calls
   "level-scoped, 20-40 families" is actually **program-and-location scoped (hundreds)**.
   The plan's own instruction to expose `enrMetaByFid` on `RosterResult` hands the
   implementer exactly the wrong set. This reintroduces the roster fan-out the plan's
   Global Constraints forbid.
2. **Two of the plan's own test snippets cannot pass.** Task 1's flagship test still
   fails after the fix (missing `eid`); Task 2's caller test references a field that
   does not exist and tries to seed a collection the test file mocks away.
3. **Task 5 under-counts the blast radius on `attendance-marker.test.tsx`** and the
   Global Constraint about "independent React state" is false for this component -
   following it literally makes the toggle tests self-cancel.

## CRITICAL

### C1 - Task 3/4: `buildAttendanceDetailIndex` is handed a PROGRAM-scoped fid set (~hundreds), not a level-scoped one (~20-40). This is the roster fan-out the plan forbids.

- **Claim (Task 3, Global Constraints line 19, Step 4 code comment):**
  > "Contacts: bounded parallel subcollection reads. This fid set is **LEVEL-scoped
  > (typically 20-40 families)**, NOT roster-scoped (867)."
  > "Chunk at 30 (Firestore's `in` cap), so a 40-family level is two queries."

- **Truth:** the only fid set the plan tells the implementer to produce is
  `enrMetaByFid` (Task 3 Step 3: *"Carry them into the `enrMetaByFid.set(...)` at `:152`
  and expose the map on `RosterResult`"*). That map is built from:

  ```ts
  // roster.ts:135-139
  const enrollSnap = await db
    .collectionGroup('enrollments')
    .where('pid', '==', level.pid)      // <- the PROGRAM period, e.g. bv-brampton-2026-27
    .where('status', '==', 'active')
    .get();
  // roster.ts:147
  if (e.location !== level.location || typeof e.fid !== 'string') continue;
  ```

  `pid` is the **offering/period for the whole program at a location**, not the level.
  Level filtering happens *later and per member*, inside `buildRoster` via
  `memberMatchesLevel(m, level, now)` (`roster.ts:83`). So
  `enrMetaByFid`/`fids` (`roster.ts:154`) = **every family with an active Bala Vihar
  enrollment at that location**, which spec §1.8 measures at ~867 families / 1,061
  children across all levels. Level 2 is ~1/12 of that.

  The repo's own fixture proves the shape: `roster-fetch.test.ts:86-93` has one level
  `brampton-level-2-...` (gradeBand `['2','3']`) and enrollments for CMT-A (grade 2),
  CMT-B (grade 3) and CMT-C (Scarborough). The pid is shared across the location; only
  location, not level, filters the enrollment scan.

- **Consequence:** Task 3 Step 4's contacts read

  ```ts
  const memSnaps = await Promise.all(
    fids.map((fid) => db.collection('families').doc(fid).collection('members').get()),
  );
  ```

  becomes **~500-800 parallel members-subcollection queries** on the eager teacher
  attendance render *and* on every `GET /api/setu/teacher/levels/[levelId]/roster`
  (`route.ts:24`). That is precisely the pattern `deriveRoster` was rewritten to kill -
  see the 19-line comment at `roster.ts:156-174` ("The old loop did 2 round-trips per
  family ... ~2N calls that made the teacher screens slow") and the regression guard
  `roster-fetch.test.ts:126-130` (`expect(fs.perFamilyMemberSubGets).toBe(0)`).
  The donations `in` chunking becomes ~20-27 queries instead of 2.

  This is the ~45s-timeout failure mode, on the page every teacher opens on launch
  Sunday.

- **Also:** the Task 3 Step 4 comment cites `student-detail.ts:62` as precedent. That
  call site reads **exactly one family's** members (`getStudentDetail(mid)`), not N.
  It is not precedent for a bounded-N loop, and the plan does not specify a cap despite
  saying "and cap it".

- **Fix:** state the fid set explicitly and derive it from the built roster, not from
  `enrMetaByFid`:
  ```ts
  const roster = await deriveRoster(levelId, date, undefined, { withConfirmation: true });
  const levelFids = [...new Set(roster.members.map((m) => m.fid))]; // LEVEL-scoped
  const detail = await buildAttendanceDetailIndex(db, levelFids, roster.enrMetaByFid);
  ```
  Add an assertion in `attendance-detail.test.ts` that a 3-level fixture sharing one
  `pid` produces detail reads for only the matched level's fids. Add an explicit hard
  cap (e.g. `if (fids.length > 80) throw`) so a future caller cannot silently pass the
  program set. And say in the Global Constraints that `deriveRoster`'s `fids` is
  program-scoped - the plan currently implies the opposite.

### M1 - Task 1 Step 1: the flagship test still FAILS after the fix. The fixture donation has no `eid`.

- **Claim (Step 4):** *"Expected: PASS, with every pre-existing test in the directory still green."*
- **Truth:** `deriveConfirmedFidsForLevel` does not confirm on "a completed donation
  exists for this fid". It confirms on `isEnrollmentConfirmed`, whose donation clause is:

  ```ts
  // apps/portal/src/app/family/_helpers/enrollment-confirmation.ts:37
  return inputs.donations.some((d) => d.status === 'completed' && d.eid === enrollment.eid);
  ```

  The plan's fixture is:
  ```ts

  ```
  No `eid`. So after the `roster-confirmation.ts:77` fix resolves the fid correctly, the
  donation is grouped into `donationsByFid` and then **discarded by the `eid` match**.
  `confirmed.has('CMT-FAM-01')` stays `false`. Step 4's "Expected: PASS" is wrong, and
  the worker cannot tell whether the production fix worked.
- **Fix:** the fixture donation needs `eid` equal to the enrollment's `eid`. Using the
  file's existing `base()` helper (`__tests__/roster-confirmation.test.ts:39-41`,
  default `eid: 'F-o'`):
  ```ts
  const enr = base({ fid: 'CMT-FAM-01', eid: 'CMT-FAM-01-o' });
  const donation = { status: 'completed', amountCAD: 200, fid: 'CMT-FAM-01', eid: 'CMT-FAM-01-o' };
  ```

### M7 - Task 3: `resolveSuggestedAmount` takes a `Date`, the plan types `enrolledAt` as `string`, and the raw Firestore field is a `Timestamp`.

- **Claim (Task 3 Interfaces + Step 3):**
  ```ts
  enrMeta: Map<string, { oid: string; enrolledAt: string; ... }>
  // roster.ts destructure:  enrolledAt?: string;
  // "expected = override ?? resolveSuggestedAmount(offering, enrolledAt) ?? snapshot"
  ```
- **Truth:**
  - `packages/shared-domain/src/setu/schemas/offering.ts:95-98`:
    `resolveSuggestedAmount(offering: Pick<OfferingDoc,'pricingTiers'>, enrollDate: Date): number`
    - the second parameter is a **`Date`**, and the return is **non-nullable `number`**.
  - `packages/shared-domain/src/setu/schemas/enrollment.ts:21`: `enrolledAt: z.date()`.
    On a raw `d.data()` read it arrives as a Firestore `Timestamp`, which is why every
    other reader converts: `report-dataset.ts:96` `enrolledAt: toDate(d['enrolledAt'])`
    with `toDate()` defined at `build-csv-rows.ts:10-15`.
  - Because the return is non-nullable, `?? snapshot` is dead. The three surfaces the plan
    cites all use the *offering-missing* fallback instead:
    `get-enrollments.ts:85-87`, `report-dataset.ts:180`, `build-csv-rows.ts:115`:
    ```ts
    override ?? (offering ? resolveSuggestedAmount(offering, enrolledAt) : snapshot)
    ```
- **Why it matters:** as specified, Task 3 fails typecheck; the naive repair
  (`new Date(enrolledAt as string)` on a Timestamp) yields `Invalid Date`, and
  `torontoYmd()` inside `resolveSuggestedAmount` (`offering.ts:102`) then throws or
  silently returns `tiers[0]` - the wrong tier. The entire point of Task 3's M2 fix is
  chip parity with the welcome roster.
- **Fix:** type it `enrolledAt: Date`, convert with the repo's `toDate()` helper in
  `roster.ts`, and state the formula as
  `override ?? (offering ? resolveSuggestedAmount(offering, enrolledAt) : snapshot)`.
  Mitigated by: the pre-push typecheck gate makes this a wasted cycle rather than a
  shipped defect, and three in-repo precedents show the conversion.

### M12 - Task 5 Step 4 omits the `data-unmarked` duplication that breaks "Next unmarked" on mobile.

- **Truth:** `jumpNext()` does

  teacher surface.
- **Fix:** scope the selector to the visible branch (e.g. `data-unmarked` only on the mobile

### M15 - Task 5 Step 4 does not reconcile spec §4.1's four-state stat cards / filter chips with the component's binary model.

- **Truth:** spec §4.1 requires **"Stat cards (4): ENROLLED · PRESENT · UNMARKED · ABSENT"**
  and **"filter chips (All / Present / Unmarked / Absent, each with a count)"**.
  `AttendanceMarker` is explicitly binary:
  ```ts
  // attendance-marker.tsx:130-137
  // Binary model: a student is Present (✓) or not. ... On Save, every not-present row is written Absent.
  const [present, setPresent] = useState<Record<string, boolean>>(...)
  ```
  and its filter is `useState<'all' | 'unmarked'>` (`:140`). There is no local "Absent" state;
  `buildMarks()` (`:205-209`) writes `absent` for everything untapped. Producing distinct
  Unmarked vs Absent counts requires a **three-state** local model seeded from
  `AttendanceViewRow.status` / `source === 'portal'` - a materially larger change than
  "stat cards, filter chips with counts". Task 5 Step 4 lists them as if they were cosmetic.
- **Fix:** either specify the three-state model migration (and what happens to the
  "tap toggles present" gesture, `markAllToggle`, and the autosave payload), or record a
  deliberate deviation that Absent stays fused with Unmarked and drop it from the chips/cards.
