# Review: P4 v2 - Adult Study Class

Plan: `docs/superpowers/plans/2026-07-25-launch-p4-adult-study-class-v2.md`
Spec: `docs/superpowers/specs/2026-07-25-adult-study-class-design.md`
Reviewed against HEAD `b1395e0`. Every file:line below was opened.

**Verdict: REQUEST CHANGES - 2 critical, 15 major, 8 minor.**

v2 fixes essentially all of v1's findings and its citation accuracy is high (calibration
list at the end). The new defects cluster in three places: (a) the success-page /
gate reconciliation, which is asserted rather than designed, (b) `enrollFamily`'s real

## CRITICAL

### C1 - Task 8 Step 4's `/family/donate/success` exemption is the pattern this repo forbids, and the plan forbids it too

**Where:** plan line 267 - `- [ ] **Step 4: Exempt \`/family/donate/success\`** - see Task 9.`

That is the entire specification. It is also a direct contradiction of the plan's own
**R1** (plan line 22): *"Never `redirect()` from a layout keyed on a header pathname."*

The gates are React server components rendered inside `app/family/layout.tsx`
(`layout.tsx:140-149`). A component has no pathname. The only way to give it one is a
header, and the repo has already paid for that:

- `apps/portal/src/app/family/layout.tsx:23-32`: *"When the completion screen was nested
  at /family/complete-profile it inherited THIS gate, which then had to exempt itself via
  the current request pathname - and under a soft client-side navigation that header is
  stale (it read '/family' while the layout re-rendered for the completion route), so the
  gate redirected to itself forever."*
- `apps/portal/src/app/complete-profile/page.tsx:6-13` records the same outage verbatim.

And the header does not exist: `middleware.ts:106-135` sets `x-portal-{role,uid,family-id,
fid,mid,extra-roles,email,phone}` via `setOrDelete` and nothing else. No `x-pathname`,
no `x-invoke-path` (grepped: zero hits repo-wide). So Task 8 Step 4 silently requires a
`middleware.ts` change that appears in no task and in no File Structure row.

Failure mode when the header reads stale: the gate believes it is on `/family` while
rendering `/family/donate/success`, redirects to `/adult-class`, and the family never
sees the ask, the pledge card, or the receipt - i.e. exactly the outcome Task 9 exists to
prevent, plus P5's card (P5 v2 line 306: *"on the donation success page **below** the
adult-class ask (P4 v2 Task 9 owns the ordering)"*).

**Fix:** pick a mechanism that does not read a pathname in the layout. Two that work:
(a) move the gate out of `app/family/layout.tsx` and into the individual `/family/*`
pages that should carry it, so `donate/success/page.tsx` simply does not render it; or
(b) move `/family/donate/success` to a top-level `/donate/success` outside the gated
layout (it already renders its own full-screen `CspRoot`, `donate/success/page.tsx:30`,
so it uses none of the layout chrome). Either way, write the decision into the plan -
this is the single load-bearing unknown in the whole document.

### C2 - The skip path and the dashboard card (Task 9 Step 4) are unreachable under the gate

**Where:** plan lines 282-284.

> *"A family who skips must be able to return, 'via the same state-driven card treatment
> the pledge uses, surfaced on the family dashboard'. The persistent `AdultClassGate`
> remains the fallback for families who skip and then navigate elsewhere."*

These two sentences cannot both be true. Spec §2.1 condition 4 is the only thing that
clears the gate, and it is satisfied only by *an active ASC enrollment carrying at least
one adult*. Skipping writes nothing. So the moment a skipper leaves the success page for
`/family`, `AdultClassGate` fires and redirects them to `/adult-class`. The dashboard card
can never render, and "skip" is not a skip - it is a one-screen detour.

No task introduces any snooze/dismissed state (contrast the pledge, which has one, and
`volunteeringSkillsNudgeDismissedAt` at `member.ts:30`, the repo's existing precedent for
exactly this).

**Fix:** decide and write down which of the two the product is. If skip is real, it needs
persistence (a `adultClassPromptDismissedAt` on the family doc, or a "prompt once per
session" cookie) and `needsAdultClassSelection` needs a sixth condition reading it. If
the gate is truly persistent per spec §2 ("keep prompting them"), delete the skip and the
dashboard card from Task 9 Step 4 and say so - do not ship a Skip button that returns the
user to the same screen.

### M2 - Task 3's reconcile + Task 10's waiver silently implement the retroactive exemption the plan says it is not implementing

**Where:** plan line 32 (Deliberate deviation 1: *"Spec §4.5 row 1 ... leaves `$601`
expected and is accepted as-is (spec open item O3, no retroactive refund)"*) vs Task 3
Step 3 (line 150) and Task 10 Step 3 (line 298).

Task 10 makes `POST /api/setu/enrollments` supply `suggestedAmountOverride: 0` whenever
`programKey === 'adult-study-class'` and `bvPaid`. Task 3 makes any *explicitly supplied*
`suggestedAmountOverride` trigger a reconcile of an existing **active** enrollment
(`enroll-family.ts:108-113` is the branch being rewritten).

So: a childless family enrolls in ASC at $101 and pays. Later they add a child, enroll in
BV, pay. They now hit `/family/enroll/adult-study-class` again (or any path that re-POSTs
that oid) - `bvPaid` is now true, the route supplies `0`, the reconcile fires, and the
$101 they already paid is rewritten to an expected of `0`. That is the retroactive
exemption O3 explicitly leaves to CMT Developer.

**Fix:** in Task 10, only apply the waiver on **create** (`created === true`), or gate the
reconcile so `suggestedAmountOverride` is written only when the stored value is `null`.
Add the test: "an ASC enrollment that already carries a non-null override is not rewritten
by a later BV-paid re-POST."

### M3 - `sumCompletedDonationsForEid` does not exist, and the nearest real helper is program-blind

### M5 - The gate is not "pure", and its per-render read cost is unaccounted

**Where:** plan line 7 - *"A **pure** `needsAdultClassSelection(family)` predicate"* - and
Task 8 Step 3 (line 263), which criticises the disclaimer gate for *"an extra Firestore

### M8 - Task 10 does not cover the BV-enrolled-but-unpaid family

ASC enroll while BV is unpaid, or write `override: 0` on any BV *enrollment* (not payment)
and accept the wider waiver. Either is fine; silence is not.

### M11 - Condition 4's "current term" scoping has no stated mechanism, and >1 open offering breaks it

**Where:** plan line 26 and Task 6 Step 5 (line 224) - *"scoping condition 4 to the
**current term**"*, with no definition.

`getOpenOfferingsForFamily` (`get-open-offerings.ts:86-104`) returns `OfferingDoc[]`.
