## CRITICAL

### C1 - Task 2 never says `sendManagedEmail` must go through `resolveSender()`, and v2's rename makes the wrong choice the natural one

**Where:** plan Task 2 Step 4 ("Implement `sendManagedEmail`"), plan lines 235-237; File Structure row
`apps/portal/src/lib/aws/send-managed-email.ts` | "`sendManagedEmail` + the narrow fallback".

Task 2 Step 4 says, in full:

> Use `err instanceof TemplateDoesNotExistException` from the SDK. Never a `.name` string compare, never `.includes()`.

That is the *only* implementation instruction. It never says which `sendSesTemplatedEmail` to call.
After Task 1 there are two importable entry points with the same name:

- `apps/portal/src/lib/aws/ses.ts` - the raw SES call (Task 1's "Produces" block declares it here, plan lines 89-95)
- `resolveSender().sendSesTemplatedEmail` - the governed one (Task 1 Step 4/Step 5)

`send-managed-email.ts` is a sibling file in the same directory as `ses.ts`. The obvious import
(`import { sendSesTemplatedEmail } from './ses'`) is the wrong one, and nothing in Task 2, Task 2's
five tests, or the File Structure table forbids it.

The consequence is exactly what spec section 3 item 2 exists to prevent:

> **This is not optional:** `resolveSender()` holds the UAT allowlist, the redirect-to-test-address branch, and the mock sender. A direct `ses.ts` call would bypass all three and mail real families from a test run.

Concretely, `resolve-sender.ts:66-67` reads `SETU_EMAIL_REDIRECT_TO` and `resolve-sender.ts:19-28`
reads `SETU_EMAIL_ALLOWLIST`; `resolve-sender.ts:51-54` routes everything to `mockSender` when
`NEXT_PUBLIC_FEATURE_CHECK_IN_NOTIFY !== 'true'`. A direct-`ses.ts` `sendManagedEmail` mails
`setu-invite`, `setu-join-request`, `payment-reminder` and `donation-thank-you` to real recipients
from every non-prod environment, and the payment-reminder cron would blast the roster.

Note this is *worse* than v1: v1 put the function only in `ses.ts` plus the interface, so there was
one obvious plumbing path. v2 deliberately created two same-named callables and then omitted the
sentence that says which one the consumer uses.

Confidence: HIGH.

**Fix:** state it in Task 2 Step 4 and pin it with a test:
- Step 4 text: "`sendManagedEmail` calls `resolveSender().sendSesTemplatedEmail(...)`. It must never import from `./ses` directly - that bypasses the allowlist, the `SETU_EMAIL_REDIRECT_TO` redirect and `mockSender` (spec section 3 item 2)."
- Add a sixth Task 2 test: `vi.mock('@/lib/aws/resolve-sender')`, assert the mocked
  `sendSesTemplatedEmail` was the thing invoked, and assert `../ses`'s `sendSesTemplatedEmail`
  was **not** called.
- Add the corresponding spec-section-6.3 test to Task 1: with `SETU_EMAIL_ALLOWLIST` set and
  `NEXT_PUBLIC_FEATURE_CHECK_IN_NOTIFY=true`, a templated send to a non-allowlisted address hits
  `mockSender.sendSesTemplatedEmail`, not `realSendSesTemplatedEmail`. Task 1 Step 1's test list
  (plan line 100) currently covers only the raw `ses.ts` shape and omits both branches, even though
  spec section 6 item 3 requires them.

## MAJOR

### M1 - Task 5 Step 2 never gates the route refusal on the flag, and Step 1 leaves the lever undecided

**Where:** plan Task 5 Step 1 (lines 316-320) and Step 2 (lines 322-326).

Step 2 says only:

> `400 { error: 'sms-signin-unsupported' }` for `type: 'phone'`.

No flag condition. Step 5 (legacy path) *does* say "behind the same flag"; Step 6 says "hide the
affordance behind `flags.smsOtp`". Step 2, the one route that matters most, says neither.

Launch spec section 8.0 is explicit that the refusal must be reversible:

> **Gating:** the block is controlled by one flag (`NEXT_PUBLIC_FEATURE_SMS_OTP`, default **off**). When SNS eventually clears the sandbox and an origination number is registered, flipping it on restores SMS sign-in

An unconditional 400 at `app/api/setu/auth/send-code/route.ts` makes the flag decorative: flipping
`NEXT_PUBLIC_FEATURE_SMS_OTP=true` would light up the UI toggle while the route keeps returning 400.

Compounding it, Step 1 leaves the server-side lever explicitly undecided:

> Consider a server-only `SETU_SMS_OTP` for the route refusals in addition to the public flag for the UI: [...] Not blocking; record whichever you choose.

So the executor cannot implement Step 2 without making an unassigned design decision, and the two
halves (UI flag, route flag) can silently diverge. `flags.smsOtp` does not exist anywhere yet
(`apps/portal/src/lib/flags.ts` has no `smsOtp`; repo-wide grep for `SMS_OTP` / `smsOtp` returns
nothing), so there is no precedent to fall back on.

Confidence: HIGH.

**Fix:** decide it in the plan. Recommend one public flag only (`flags.smsOtp`, read on both sides,
matching every other `NEXT_PUBLIC_FEATURE_*` in `lib/flags.ts`), and rewrite Step 2 as
"`if (type === 'phone' && !flags.smsOtp) return 400 { error: 'sms-signin-unsupported' }`". Delete
the "record whichever you choose" sentence. Add a test that with the flag on, `type:'phone'` still
reaches `sendSMS`.

### M6 - Task 2 Step 6 overstates what `ConfigurationSetName` buys: Rendering Failure never reaches the application

**Where:** plan Task 2 Step 6 (lines 241-245), headed "Wire a configuration set so render failures are
not silent", and the framing at lines 37-43.

The SDK text the plan quotes is accurate. Verified at
`node_modules/.pnpm/@aws-sdk+client-ses@3.1030.0/node_modules/@aws-sdk/client-ses/dist-types/commands/SendTemplatedEmailCommand.d.ts`
lines 69-73. But the very next sentence of that same block (lines 75-77) is the one that decides what
the fix buys:

> For these reasons, we highly recommend that you set up Amazon SES to send you **notifications** when Rendering Failure events occur.

An SES configuration-set event destination publishes to SNS / CloudWatch / Kinesis Firehose. It is
strictly out-of-band. With `ConfigurationSetName` set:

- `client().send(...)` still resolves successfully with a `MessageId`
  (`SendTemplatedEmailResponse` at `models_0.d.ts:3311-3319` has only `MessageId`)
- `sendManagedEmail` still logs a send and still does not fall back
- the recipient still gets nothing

Nothing about the application's behaviour changes. The step is worth doing, but it is an *alerting*
measure for whoever watches the SNS topic, not a correctness measure - and the plan names no
consumer, no topic, no alarm, and no owner for watching it. As written ("so render failures are not
silent") a reader closes the M1 gap in their head that is not actually closed: for the `setu-invite`
the mail is still silently lost, exactly as line 43 describes.

Confidence: HIGH.

**Fix:** retitle Step 6 to what it is ("route render failures to an out-of-band alarm; the
application still cannot see them") and state plainly that the in-application gap remains open. Then
promote the thing that actually closes it - the per-template UAT send gate now buried in Step 6's
last paragraph - to a numbered, non-optional Task 6 step with a checkbox per template, since by the
plan's own admission it is "the **only** other thing standing between a bad template and silent loss."

### M7 - Task 2 Step 6 introduces a new hard-failure mode the plan's own fallback rule refuses to catch

**Where:** plan Task 2 Step 6 (line 243): "Pass it from `SES_CONFIGURATION_SET`".

`ConfigurationSetDoesNotExistException` is in the command's declared throws -
`SendTemplatedEmailCommand.d.ts:135-136`:

> @throws {@link ConfigurationSetDoesNotExistException} (client fault) Indicates that the configuration set does not exist.

Under the plan's own matrix (Task 2 Step 1 test 3, lines 210-213): "does NOT fall back on any other
SES failure". So a `SES_CONFIGURATION_SET` that is misspelled, or that exists in a different region
than `AWS_SES_REGION` (default `ca-central-1` per `apps/portal/src/lib/env.ts`, and SES configuration
sets are region-scoped exactly like templates - spec section 5), makes **every one of the five
managed emails throw with no fallback**. Today, and under the plan without Step 6, the same
misconfiguration would be impossible.

Blast radius is worst where the plan already flagged it: `app/api/setu/invite/send/route.ts:175-178`
sends after the transaction commits and does not catch, so this is a 500 with the invite row already
written; `features/check-in/notifications/payment-reminder-service.ts:31` throws before
`ref.set({ lastReminderSentAt })` at `:37`, so the cron retries forever.

Realist note: it needs an operator to set the var wrong, and it fails loudly and immediately rather
than silently, so it is MAJOR and not CRITICAL - but the plan adds the failure mode and never names
it, and `SES_CONFIGURATION_SET` is a launch-day env var going into the cutover checklist where a
typo is a live possibility.

Confidence: HIGH.

**Fix:** in Task 2 Step 6, require that `ConfigurationSetName` is omitted entirely when
`SES_CONFIGURATION_SET` is unset (not passed as `undefined` by accident through a spread), and add
`ConfigurationSetDoesNotExistException` to the fallback matrix as its own row: log at error and
**retry once without the configuration set** rather than failing the send. Add it as a sixth test.
Also record in Task 6 that the configuration set must live in `AWS_SES_REGION`.
