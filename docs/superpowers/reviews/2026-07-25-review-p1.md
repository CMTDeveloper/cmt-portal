# Review: P1 - Coordinator Role & Staff Cross-Family Edit

- **Plan:** `docs/superpowers/plans/2026-07-25-launch-p1-roles-and-cross-family-edit.md`
- **Spec:** `docs/superpowers/specs/2026-07-24-aug-3-launch-batch-design.md` §2, §3
- **Baseline verified against:** `main` @ `b1395e0`
- **Verdict: REQUEST CHANGES.** 7 critical, 14 major, 7 minor.

**Headline:** the plan implements the coordinator role *only at the middleware layer*. Every page and API it grants has a second, independent in-handler/in-layout role gate that the plan never touches. All 6 API grants and both page grants 403 or render "Access denied" for a coordinator. The `can-access-route` unit tests in Task 3 would pass green while the feature is 100% non-functional - the exact "green tests but broken in prod" failure CLAUDE.md §Pre-ship verification exists to prevent.

**Fix:** add a task that updates all 9 handlers to `isAdmin(session) || isCoordinator(session)` (and `|| isWelcomeTeam(session)` where it exists today). Add a route-handler test per file. Task 3 must not be considered complete on a green `can-access-route.test` alone.

### C2. `/admin/layout.tsx` renders "Access denied" for any non-admin. The `/admin/programs` + `/admin/levels` page grants are dead.

### C4. Task 3 Step 3's placement instruction contradicts its own blockquote and, as literally written, REVOKES welcome-team's teacher assignment.

### C6. A coordinator who is not also a parent can never obtain a session.
