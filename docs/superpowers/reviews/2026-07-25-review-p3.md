## CRITICAL

### C1 - Task 3 + Task 4: the migration point does not exist, and the one that does also carries OTP
**Task/step:** Task 3 Files + Step 3; Task 4 Step 1/2.

**Claim:** Task 3 modifies `apps/portal/src/features/check-in/shared/notifications/send-email-service.ts:13` to migrate `payment-reminder` and `donation-thank-you`. Task 4 asserts the OTP exemption via `await sendOtpEmail({ to, code })` and says Step 2 will "PASS immediately - Task 3 never touched the OTP path".

**Truth:** three separate errors.
1. That path does not exist. `apps/portal/src/features/check-in/shared/notifications/` contains **only** `mock-sender.ts`. The real file is `apps/portal/src/features/check-in/notifications/send-email-service.ts` (no `shared/` segment). The spec gets this right; the plan does not.
2. That file has **no per-template call site to migrate**. It is a single generic wrapper:
   ```ts
   // features/check-in/notifications/send-email-service.ts:11-20
   export async function sendTemplatedEmail(args: SendTemplatedEmailArgs): Promise<void> {
     const rendered = (renderEmailTemplate as any)(args.template, args.props);
     const sender = resolveSender();
     await sender.sendEmail({ to: args.to, subject: rendered.subject, text: rendered.text, html: rendered.html });
   }
   ```
   `args.template` is `'otp-code' | 'payment-reminder' | 'donation-thank-you'`. Rewriting this body to call `sendManagedEmail` routes **otp-code through the managed SES path**, which is exactly what the whole plan (and spec section 1.1) exists to prevent. There is no instruction anywhere in Task 3 to branch on the template name.
3. `sendOtpEmail` **does not exist** anywhere in `apps/portal/src` or `packages`. Task 4's test cannot be written as given, and Step 2's "Expected: PASS immediately" is impossible.

The actual call sites the plan needed to name:
- `payment-reminder` -> `apps/portal/src/features/check-in/notifications/payment-reminder-service.ts:31`
- `donation-thank-you` -> only producer is `apps/portal/src/app/api/check-in/notifications/send-email/route.ts:18`, driven by `apps/portal/src/features/check-in/admin/send-donation-email-button.tsx:26`
- `otp-code` -> same generic route (`send-email/route.ts:8` zod enum). Note the **live Setu sign-in OTP does not use this path at all**: `app/api/setu/auth/send-code/route.ts:150-159` builds subject/text inline and calls `resolveSender().sendEmail` directly.

**Fix:** rewrite Task 3's Files list to the two real call sites above; leave `send-email-service.sendTemplatedEmail` as the in-code render path (or branch inside it so `otp-code` never reaches `sendManagedEmail`); retarget Task 4's test at the real OTP senders (`send-email-service.ts` with `template:'otp-code'`, and `setu/auth/send-code/route.ts`).

### C2 - Task 1: `sendTemplatedEmail` and `SendTemplatedEmailArgs` already exist with incompatible shapes
**Task/step:** Task 1 Interfaces / Step 3.

**Claim:** Task 1 "Produces" `SendTemplatedEmailArgs { to; templateName; data }` and `sendTemplatedEmail(args)` in `lib/aws/ses.ts`, presented as new symbols.

**Truth:** both names are already taken, meaning the opposite thing:
```ts
// features/check-in/notifications/send-email-service.ts:4-11
export interface SendTemplatedEmailArgs { to: string; template: TemplateName; props: Record<string, unknown>; }
export async function sendTemplatedEmail(args: SendTemplatedEmailArgs): Promise<void>
```
Existing consumers: `payment-reminder-service.ts:4,31`, `app/api/check-in/notifications/send-email/route.ts:3,18`, plus three test files that `vi.mock` the module **by that export name** (`send-email.test.ts:5`, `payment-reminder-service.test.ts:22`, `send-email-service.test.ts:16`). After Task 1 the codebase has two exported `sendTemplatedEmail` with different arg shapes, where "templated" means SES-side in one and in-code in the other - and Task 3 edits both files in the same commit.

**Fix:** name the new pair `sendSesTemplatedEmail` / `SendSesTemplatedEmailArgs` (or rename the legacy one to `sendRenderedEmail`). Do not ship both under one name.

### C3 - Task 5: the register -> sign-in phone handoff becomes a hard dead end
**Task/step:** Task 5 Step 4/5.

**Claim:** Step 5 - "Phone capture is untouched everywhere else"; spec section 8.0 - safe because all 867 families are email-reachable.

**Truth:** the portal deliberately routes phone-matched families into the phone sign-in path.
- `app/register/page.tsx:434` - ``href={`/sign-in?type=${match.matchedType}&value=${encodeURIComponent(match.matchedValue)}`}``
- `app/register/__tests__/page.test.tsx:185` - `expect(href).toBe('/sign-in?type=phone&value=4165550000')` (an existing, passing assertion)
- `app/sign-in/page.tsx:174` - `const initialContactType: ContactType = prefillType === 'phone' ? 'phone' : 'email';`
- `app/sign-in/page.tsx:179-191` - `hasOtpHandoff` **forces** OTP mode and suppresses the saved password preference.

So a returning family whose lookup matched on **phone** lands on `/sign-in` pre-set to Phone with their number filled in, and under Task 5 gets a 400. They were matched by a contact the portal holds; they may not know which email is on file, and the password fallback is suppressed for exactly this handoff. "Email covers everyone" is true of the roster and false of this flow.

**Fix:** when a `type=phone` handoff arrives and `!flags.smsOtp`, land on the Email tab with an explicit "we recognised your number - sign in with the email on your account" notice; or make `register/page.tsx:434` hand off only when `matchedType === 'email'`. Add a test alongside the updated `page.test.tsx:185`.

## MAJOR

### M1 - Task 2: the matrix misses SES's silent render failure, which is worse than today for the invite
**Task/step:** Task 2 Step 4 (matrix), spec section 4.1.

**Claim:** three rows cover it - not configured, template-not-found, everything else.

**Truth:** there is a fourth state the matrix cannot see. From the installed SDK's own docs (`@aws-sdk/client-ses@3.1030.0`, `dist-types/commands/SendTemplatedEmailCommand.d.ts`, command description):

> "If your call to the `SendTemplatedEmail` operation includes all of the required parameters, Amazon SES accepts it and returns a Message ID. However, if Amazon SES can't render the email because the template contains errors, it doesn't send the email. Additionally, because it already accepted the message, Amazon SES doesn't return a message stating that it was unable to send the email."

A template that **exists but fails to render** resolves successfully. `sendManagedEmail` logs a send, no fallback fires, and nothing is delivered. For `setu-invite` - which the plan itself calls load-bearing for launch - that is silent loss, strictly worse than today's behaviour. Spec section 4.1's caveat only anticipates the milder "renders with blanks" case.

**Fix:** `SendTemplatedEmailRequest` accepts `ConfigurationSetName` (`models_0.d.ts` within the `SendTemplatedEmailRequest` block, alongside `Template`/`TemplateData`). Set it, point it at an SES configuration set publishing **Rendering Failure** events, and make that a Task 2 step plus an O2 prerequisite for Vaibhav. If deferred, record it as an accepted risk in the runbook and make the per-template UAT send (spec section 6.1) a hard gate before each `SES_TEMPLATE_*` var is set in prod.

### M2 - Task 4: the OTP "pin" is vacuous; the exemption is convention, not code
**Task/step:** Task 4 Step 1, both tests.

**Claim:** "The exemption is enforced in code - not by the mere absence of a template."

**Truth:** nothing in the plan enforces it.
- Test 1 calls `sendOtpEmail`, which does not exist (see C1).
- Test 2 is a tautology:
  ```ts
  const names: ManagedEmailName[] = ['payment-reminder','donation-thank-you','setu-invite','setu-join-request','pledge-activated'];
  expect(names).not.toContain('otp-code' as never);
  ```
  The array is a literal the test itself writes. If someone adds `'otp-code'` to `ManagedEmailName`, this array still typechecks (a subset is always assignable) and the assertion still passes. The test **cannot fail**, so it guards nothing - which is the precise failure mode Task 4 was written to prevent.

**Fix:** enforce at compile time plus runtime:
```ts
type _OtpNotManaged = 'otp-code' extends ManagedEmailName ? never : true;
const _assertOtpNotManaged: _OtpNotManaged = true;
```
plus a guard inside `sendManagedEmail` that throws on any otp-ish `name`, plus a real behavioural test against the actual OTP senders named in C1.

### M3 - Task 1 Step 4: the interface is not called `Sender`, and the mock implements a different one
**Task/step:** Task 1 Step 4 (and Architecture paragraph).

**Claim:** "add `sendTemplatedEmail(args)` to `Sender`" at `resolve-sender.ts:7-8`.

**Truth:** the cited lines are right, the name is not, and the change is wider than stated:
- `resolve-sender.ts:6-9` declares `export interface ResolvedSender` (no `Sender` exists).
- `features/check-in/shared/notifications/mock-sender.ts:13-16` declares a **separate** `NotificationSender`, and `mockSender` is typed against it.
- `mockSender` is used as a `ResolvedSender` at `resolve-sender.ts:53` (`return mockSender`) and as the allowlist-drop target at `:85` and `:113`.

Adding the method to `ResolvedSender` alone fails typecheck at all three sites. Both interfaces must change in the same commit.

**Fix:** name `ResolvedSender` and `NotificationSender` explicitly in Step 4 and state that both gain the method.

### M4 - Task 1 Step 4: the redirect safety net cannot carry its intended-recipient marker for templated sends
**Task/step:** Task 1 Step 4; spec sections 5 and 6.3.

**Claim:** "implement it in the real sender with the **same** allowlist and redirect branches the existing `sendEmail` uses."

**Truth:** not literally implementable. The redirect branch works by rewriting the subject:
```ts
// resolve-sender.ts:74
await realSendEmail({ ...args, to: emailRedirectTo, subject: `[test → ${args.to}] ${args.subject}` });
```
A templated send has no subject in code - it lives in SES. Every redirected templated email arrives in the tester's single inbox with an identical SES subject and no indication of who it was for, destroying the exact signal `SETU_EMAIL_REDIRECT_TO` exists to provide. Same problem for the mock, which logs `subject` and `text` (`mock-sender.ts:24-28`) - neither exists on a templated send.

**Fix:** inject the marker as a reserved template variable (e.g. `_testRecipient`) that SES templates render when present, add it to the runbook variable contract so Vaibhav includes it, and specify what the mock records for a templated call.

### M5 - Task 2/3: "what if the fallback also fails" is unspecified
**Task/step:** Task 2 Step 4; Task 3 Step 3.

**Claim:** the matrix has three rows and Task 2 Step 5 expects "PASS, all four cases".

**Truth:** no row says which error surfaces when the **fallback** `sendEmail` throws after a template-not-found. This matters concretely at the invite: `app/api/setu/invite/send/route.ts:175-178` sends after the transaction commits and does not catch, so a throw becomes a 500 with the invite row already written. Whether the caller sees `SesTemplateNotFoundError` or the underlying SES error changes debuggability and any future retry logic.

**Fix:** specify "the SES template-not-found error is logged and swallowed; a fallback failure propagates unchanged" and add it as a fifth test.

### M6 - Task 5 Step 5: the sign-in page duplicates the whole form; one line range covers half of it
**Task/step:** Task 5 Files + Step 5.

**Claim:** modify `sign-in/page.tsx:234-254`; "Update the hint at `:237-239` and the placeholder at `:236`". "Keep the Phone tab visible."

**Truth:** the cited lines are correct for the shared consts (`:234` `contactLabel`, `:236` `contactPlaceholder`, `:237-239` `contactHint`), but the interactive parts are duplicated across two full layouts:
- toggle + submit, mobile: `:603-621`
- toggle + submit, desktop: `:719-737`
- shared handler: `handleSendCode` at `:241-275`

An implementer patching only `:234-254` gets the notice (shared const) but leaves **both** submit buttons live, so "block submission client-side" silently does not happen. Also, there is no "Phone tab" - it is a toggle button labelled "Use phone number instead" (`:620`, `:736`); the plan's vocabulary will send someone hunting for a tabs component.

**Fix:** enumerate all four sites and require the guard inside `handleSendCode` so both layouts are covered by construction rather than by patching each.

### M7 - Task 5: two other live SMS-OTP paths are left broken, one of them the legacy production entry point
**Task/step:** Task 5 (whole) + Self-Review.

**Claim:** the Self-Review lists only the deliberately-skipped `sns.ts` `+1` guard as uncovered.

**Truth:** two other routes still send SMS OTPs that reach nobody, and neither is mentioned:
1. **`/api/auth/family/send-code`** - `route.ts:48-56` still branches to `resolveSender().sendSMS`, and its UI still offers a Phone tab (`features/check-in/family/family-login-form.tsx:81-85`, `:12`). CLAUDE.md states legacy `/login` + `/check-in/*` is still the production entry point for existing BV families. Those users keep getting today's silent nothing - the exact bug Task 5 exists to fix. The prompt asked whether Task 5 breaks this path: it does not break it, but it also does not fix it, and the plan never says so.
2. **`/api/setu/contacts/send-code`** - `route.ts:74-76` SMSes a code to verify a phone being **added to a profile**. Spec section 8.4 records this as a known, non-blocking limitation *for non-`+1` numbers* under the old NANP-gate design. Under the new "no SMS at all" posture it is broken for **every** number, including Canadian ones - a materially larger regression than section 8.4 describes. The plan inherits 8.4's wording without re-scoping it, and Step 5's "profile all keep accepting any country's number" is therefore misleading: capture is untouched, but the verification that gates it is dead.

**Fix:** decide and document both. Minimum: re-scope the 8.4 limitation in the plan and add a Task 5 step hiding the legacy phone tab and the profile add-phone flow behind the same `flags.smsOtp`.

## MINOR

### m1 - Task 5 Step 3: `NEXT_PUBLIC_` flag read inside a route handler
`flags.smsOtp` is consumed server-side in `send-code`/`verify-code`. Every existing `NEXT_PUBLIC_FEATURE_*` in `lib/flags.ts` is fine to read on the server, so this works - but a public flag is the wrong lever for a server-side refusal, since anyone can read the posture from the bundle and it must be set at build time, not flipped at runtime. Consider a server-only `SETU_SMS_OTP` for the routes plus the public one for the UI. Not blocking. The plan is correct that it must be added to `turbo.json`'s `env` array - it is currently absent (`turbo.json:12-56`).

### m2 - Task 1 Step 0: SDK facts verified offline; results below (Step 0 can be closed)
Verified against the installed `@aws-sdk/client-ses@3.1030.0` (pinned `^3.700.0` at `apps/portal/package.json:54`; no `client-sesv2` in the tree, so "SES v1 classic" is correct):

## Answers to the specific questions asked

**2 - AWS SDK usage.** Verified offline, no doc fetch needed. `@aws-sdk/client-ses` is SES v1 classic; `SendTemplatedEmailCommand` exists; `Template` + `TemplateData` (JSON string) is the right shape; `TemplateDoesNotExistException` is the right error name and is in the command's declared throws. See m2 for exact file:line evidence and two cautions. **Nothing here needs must-verify treatment** - Task 1 Step 0 is already satisfied.

**3 - Is the fallback matrix implementable? Double-send? Fallback also fails?**
Implementable as three rows, yes. **No double-send risk in the designed matrix** - the only fallback triggers are "never attempted" and `TemplateDoesNotExist`, and SES does not queue a message it rejects for a missing template, so the rows are sound and the plan's reasoning in Task 2 Step 1 test 4 is correct. The two real gaps are **M1** (a fourth, invisible state: template exists but fails to render -> resolves OK, nothing delivered, no fallback) and **M5** (fallback-also-fails is unspecified).

**4 - Do the four migrations preserve current behaviour with no SES template?**
- `setu-invite` (`invite/send/route.ts:175-178`) - **yes**, provided the fallback is `() => setuInviteEmail(props)` and errors propagate unchanged. Post-transaction, uncaught, so today's semantics are a 500 after the invite row is written; the matrix preserves that. Caveats M1 and M5 apply, and M1 hits this email hardest.
- `setu-join-request` (`join-request/send/route.ts:65-73`) - **yes**, and it is the safest of the four: wrapped in `Promise.allSettled` so nothing propagates either way.
- `payment-reminder` - **cannot be assessed as written**; the plan's call site does not exist. Real site is `payment-reminder-service.ts:31`. Note it writes `lastReminderSentAt` **after** the send (`:37`), so a rethrow leaves the idempotency window unset and the next cron retries - preserved either way, but should be stated.
- `donation-thank-you` - **cannot be assessed as written**; same reason. Real site is `api/check-in/notifications/send-email/route.ts:18`, which is the shared OTP dispatcher - see C1.

**5 - Task 5 SMS refusal.**
- (a) **Anti-enumeration is preserved.** The refusal keys purely on `type === 'phone'` from the parsed body, before `findSetuFamilyByContact` at `route.ts:72` and before the silent-200 at `:128-135`. Every phone input gets an identical 400 whether or not the number is registered, so there is no differential and no oracle. Placing it before the rate limit at `:51` is also fine - it does strictly less work, and no rate-limited path is bypassed because nothing downstream runs. The plan is correct here.
- (b) **It does not break the legacy path** - `/api/auth/family/send-code` is a different route file and is untouched. But it also does not **fix** it, and that route still SMSes (`route.ts:48-56`) from a UI that still offers Phone (`family-login-form.tsx:81-85`) on what CLAUDE.md calls the current production entry point. Unacknowledged in the Self-Review. See M7.
- (c) **Phone capture is genuinely untouched** in registration and member add/edit - registration verifies by email only (`register/family/page.tsx:358-364` hardcodes `type: 'email'`). **But** the claim overreaches: `/api/setu/contacts/send-code:74-76` (add a phone to an existing profile) requires an SMS OTP and is now dead for **all** numbers, not just non-`+1` as spec 8.4 says. See M7. And the register->sign-in phone handoff is a hard dead end - see C3.

**6 - Is the OTP exemption enforced in code?**
**No. It is convention only**, despite Task 4's comment claiming otherwise. Both of Task 4's tests are non-functional: one calls a function that does not exist, the other is a tautology that cannot fail. Worse, as written Task 3 would actively route `otp-code` through the managed path, because the only file it names is the shared three-way dispatcher. See C1 and M2.

## Positive observations

- The narrow-fallback reasoning (Task 2 Step 1 test 4, spec 4.1 row 3) is correct and well argued - refusing to fall back on throttles/auth/network is the right call and the double-send analysis holds up.
- Insisting the new method join the sender interface rather than calling `ses.ts` directly is right: `resolve-sender.ts:50-127` is genuinely the only thing standing between a test run and 867 real families.
- The anti-enumeration positioning in Task 5 is correct and correctly justified - shape-based refusal before any lookup is exactly the right rule, and it matches spec 8.3.
- Task 1 Step 0 refusing to trust training data for the SDK signature is good discipline; it happens to have been right, which is the best kind of verification outcome.
- Keeping the code templates as a fallback layer rather than deleting them (spec 4.2 amending 3.5) removes the launch-week cliff, and the plan carries that through consistently in Task 3 Step 4.
- The variable-contract-as-test idea (Task 3 Step 1) is the correct answer to an untyped cross-system boundary.
