# CRITICAL

## CRITICAL-1 - Sentry ships the plaintext bank details on the first unhandled error

> ### ⚠️ CORRECTED 2026-07-25 - this finding was overstated, and its suggested fix was harmful
>
> **Status: RESOLVED in code** (`apps/portal/src/lib/sentry/scrub-event.ts`, wired into all
> three init sites). Read this box before anything below it.
>
> **What the reviewer got wrong.** It read the `@default` JSDoc annotations in
> `datacollection.d.ts`. Those document the `DEFAULTS` constant, **not** the effective
> value when `dataCollection` is absent. The actual resolution is in
> `@sentry/core@10.62.0/build/esm/utils/data-collection/resolveDataCollectionOptions.js`:
>
> ```js
> const base = options.dataCollection != null
>   ? DEFAULTS                                                // permissive
>   : defaultPiiToCollectionOptions(options.sendDefaultPii);  // restrictive when pii off
> ```
>
> With neither option set - the repo's state at `b1395e0` - the restrictive branch applied:
> **`httpBodies: []`**, `userInfo: false`, cookies/headers/query params deny-listed. So claims
> 1 and 3 below are false: **request bodies were never being captured, on server or client.**
> Claim 2 is false in effect too - `stackFrameVariables` did default to `true`, but nothing in
> v10.62.0 consumes it; `localVariablesIntegration` no-ops unless `includeLocalVariables: true`
> is also set, and it never was. Claim 4 (console breadcrumbs) is correct.
>
> **What the reviewer got right.** There was no `beforeSend` scrubber, the SDK's privacy
> posture was implicit rather than pinned, and spec §4.2 rule 4 / §8 asserted "never sent to
> Sentry" as a control that nothing implemented. That is a real gap and it is now closed.
>
> **The suggested fix below would have made things worse.** The partial
> `dataCollection: { userInfo, httpBodies, stackFrameVariables }` object is precisely the trap:
> passing the object at all flips every *omitted* field to the permissive `DEFAULTS`, so
> `cookies`, `httpHeaders` and `queryParams` would have gone from deny-listed to fully
> collected - including the Firebase session cookie. **A partial object is worse than none.**
>
> **What shipped instead:** all 8 fields pinned in one shared isomorphic module
> (`cookies: false`, `httpBodies: []`, `userInfo: false`, `stackFrameVariables: false`,
> deny-lists on headers/query params), plus a key-based `beforeSend`/`beforeSendTransaction`
> scrubber covering `extra`, `contexts`, breadcrumb data, request data and stack-frame vars.
> 13 unit tests. `includeLocalVariables` is documented as never-set.
>
> **Still open, and a decision for the owner:** emails and phone numbers are interpolated into
> `console.log` strings in `resolve-sender.ts`, `sns.ts` and `send-code/route.ts`, which become
> Sentry breadcrumb *messages*. Key-based redaction cannot reach positional string args. That
> is the *other* half of `SECURITY_REVIEW_2026-07-22.md:716-749` (rated Medium) and it is not
> fixed. No OTP is logged - `send-code` logs a `hash=` prefix only.

**Task:** Task 4 (routes) - and a missing task before it.
**OWASP:** A09 Logging & Monitoring Failures / A02 Cryptographic Failures (plaintext egress).
**Exploitability:** No attacker needed. One 500 in `POST /api/pledges` does it.
**Blast radius:** Full plaintext bank details (institution, transit, account) for every family that hits an error, permanently retained in a third-party SaaS, readable by anyone with Sentry access, outside all of this design's controls.

Spec §4.2 rule 4 and §8 both assert bank details are "never sent to Sentry". **Nothing in the plan implements that, and the current defaults do the opposite.**

Verified in `node_modules/.pnpm/@sentry+core@10.62.0/.../types/datacollection.d.ts`:

```
httpBodies?: HttpBodyCollectionTarget[];
  @default ['incomingRequest', 'outgoingRequest', 'incomingResponse', 'outgoingResponse']

stackFrameVariables?: boolean;
  @default true

frameContextLines?: number;
  @default 5
```

And `apps/portal/src/sentry.server.config.ts:27-33` has the opt-out **commented out**:

```ts
// dataCollection: {
//   // To disable sending user data and HTTP bodies, uncomment the lines below:
//   userInfo: false,
//   httpBodies: [],
// },
```

So today, on `@sentry/nextjs` 10.62.0:

1. **`incomingRequest` bodies are captured.** Any exception in the `POST /api/pledges` handler - a Zod throw, a Firestore contention error, a missing `PLEDGE_ENCRYPTION_KEY`, an OOM - attaches the raw JSON request body, which *is* the four bank fields in plaintext.
2. **`stackFrameVariables: true` captures locals.** An exception thrown inside `encryptBankDetails(details)` serializes the local `details` object into the stack frame. This fires even if you fix (1).
3. **`outgoingRequest` is captured client-side too.** `instrumentation-client.ts` runs the same defaults, so the browser SDK can attach the outbound fetch body of the pledge form submit.
4. Console breadcrumbs are on by default, so any `console.error('[pledges] ...', input)` also lands in Sentry.

There is **no `beforeSend` scrubber anywhere in the repo** (grepped `apps/portal/src` for `beforeSend`/`scrub`: zero hits).

The external audit already flagged exactly this file. `SECURITY_REVIEW_2026-07-22.md:712-735` lists `apps/portal/src/sentry.server.config.ts:15-31` under *"Structured Sentry logging is enabled without repository-defined scrubbing."* That finding is **open**. The plan proposes to add bank account numbers to a system with a known-open observability-leak finding, and cites that same finding approvingly in spec §8 as something it "sidesteps".

**Fix - add a Task 0 that lands before any pledge route exists.** Three layers, all cheap:

```ts
// apps/portal/src/sentry.server.config.ts  (and .edge.config.ts, and instrumentation-client.ts)
Sentry.init({
  dsn: SENTRY_DSN,
  integrations: [nodeProfilingIntegration()],
  enableLogs: true,
  tracesSampleRate: isDev ? 1.0 : 0.1,
  profileSessionSampleRate: isDev ? 1.0 : 0.1,
  profileLifecycle: 'trace',

  // Bank details (P5) must never leave the process. These defaults are
  // opt-OUT in SDK v10 — httpBodies defaults to all four targets and
  // stackFrameVariables defaults to true.
  dataCollection: {
    userInfo: false,
    httpBodies: [],
    stackFrameVariables: false,
  },

  // Belt-and-braces: a redaction pass keyed on the field names themselves,
  // so a future SDK default change or a stray console.error cannot leak.
  beforeSend(event) {
    return redactBankFields(event);
  },
  beforeBreadcrumb(crumb) {
    return redactBankFields(crumb);
  },
});
```

with a shared, unit-tested `redactBankFields` that walks the object and replaces the value of any key matching `/^(bankNumber|transitNumber|institutionNumber|accountNumber)$/i` with `'[redacted]'`.

Third layer, in the route itself - never let the raw body become a variable that can be captured:

```ts
// apps/portal/src/app/api/pledges/route.ts
export async function POST(req: Request) {
  const session = readSessionFromHeaders(req);
  if (!session || !isSetuManager(session) || !session.fid) {
    return NextResponse.json({ error: 'no-session' }, { status: 401 });
  }
  try {
    // Parse INSIDE the try so a malformed-JSON throw cannot escape with the body attached.
    const parsed = SubmitPledgeSchema.safeParse(await req.json());
    if (!parsed.success) {
      // NEVER echo parsed.error — Zod issues can carry `received` values.
      return NextResponse.json({ error: 'bad-request' }, { status: 400 });
    }
    const { pid } = await submitPledge({ fid: session.fid, mid: session.mid, input: parsed.data });
    return NextResponse.json({ ok: true, pid }, { status: 200 });
  } catch {
    // Deliberately swallow the cause. Do NOT `console.error(e)` and do NOT
    // Sentry.captureException(e) here — the exception's stack frames hold the
    // bank details. Log only a correlation id.
    return NextResponse.json({ error: 'server-error' }, { status: 500 });
  }
}
```

**Test to add** (Task 4 Step 1): call `POST /api/pledges` with `submitPledge` mocked to throw, capture the Sentry event via `beforeSend`, and assert the serialized event contains none of the four field names or the submitted account number.

## CRITICAL-2 - `pledge_secrets` protection rests on unversioned Firestore console config, and the client SDK is already wired

**Task:** Task 4 (and spec §8.2, which dismisses this).
**OWASP:** A01 Broken Access Control / A05 Security Misconfiguration.
**Exploitability:** Remote, authenticated as any family (they all have Firebase Auth accounts) - **if and only if** the deployed rules are permissive. Unknown from the repo, which is the problem.
**Blast radius:** Direct read of every `pledge_secrets` document (ciphertext + iv + authTag) and, worse, **write** access to `pledges` - letting a family set their own `status: 'active'`.

Verified:
- **No `firestore.rules` exists.** `firebase.json` declares `{"firestore": {"indexes": "firestore.indexes.json"}}` and nothing else. There is no rules file anywhere in the repo.
- **The client Firebase SDK is initialized and `getClientFirestore()` is exported** - `packages/firebase-shared/src/client.ts:3,41-43`. Nothing calls it today, but the app, the public API key (`NEXT_PUBLIC_PORTAL_FIREBASE_API_KEY`), and an authenticated Firebase user session all exist in every family's browser.

Spec §8.2 acknowledges this and concludes *"Encryption is what makes that residual tolerable... Tracking rules in-repo is worth doing, but is not gated on this feature."*

**That reasoning does not survive contact with the actual asset.** Encryption makes the *secret* leak survivable, but it does nothing for the `pledges` collection - if rules are open, a family can flip their own pledge to `active`, which is exactly the "unverified money counted as real" risk spec §8 claims to have closed. And "no read path exists at all" (spec §8, the design's headline control) is only true of the *HTTP* surface; the *database* surface is unmanaged.

The fix costs about ten minutes and it is the only control here that is enforced below the application:

```
// firestore.rules  (repo root)
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // The portal reaches Firestore exclusively through the Admin SDK, which
    // bypasses rules. Nothing legitimate uses the client SDK for data, so
    // deny everything: a future client-side read is then a loud failure,
    // not a silent exposure.
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

```json
// firebase.json
{
  "firestore": {
    "rules": "firestore.rules",
    "indexes": "firestore.indexes.json"
  }
}
```

Deploy with `firebase deploy --only firestore:rules --project chinmaya-setu-uat` first, run the full E2E to prove nothing regressed (it will not - nothing reads client-side), then prod. Note this is `firestore:rules`, **not** `firestore:indexes`, so the repo's "never `--force` an index deploy against 715b8" rule does not apply; rules deploys do not touch indexes. Confirm with the standalone `chinmaya-family-check-in` app's owner that it also uses Admin SDK only before deploying rules to shared prod `715b8`.

**Also verify before launch** (a two-minute console check, not a code change): whether the prod database is in "test mode" (`allow read, write: if request.time < ...`), which is the failure case that turns this from theoretical to live.

# MAJOR

## MAJOR-1 - Confirm/cancel/submit handlers have no role check of their own; middleware is the only gate

**Task:** Task 4, Steps 3-4.

The plan describes the handlers as "manager-only" and "admin-only" but the only enforcement it specifies is the `canAccessRoute` clause. Every comparable route in this repo re-checks in the handler - e.g. `apps/portal/src/app/api/setu/donations/route.ts:19-22` does `readSessionFromHeaders` then `isSetuFamily(session)` then 401, *after* middleware already authorized it.

Two consequences:
1. A single edit to `can-access-route.ts` (adding a welcome-team clause above the pledge clause, say) silently opens a financial endpoint with no second gate.
2. **The plan's own security test cannot pass without it.** `POST_CONFIRM(pid, WELCOME)` calls the route handler directly in vitest - middleware does not run in that harness. With no handler-level check, that test returns 200 for welcome-team and the "confirm is admin-only" assertion fails, or worse, gets "fixed" by asserting the middleware layer instead and never exercising the handler.

**Fix.** In every pledge handler:

```ts
// apps/portal/src/app/api/admin/pledges/[pid]/confirm/route.ts
const session = readSessionFromHeaders(req);
if (!session || !isAdmin(session)) {
  return NextResponse.json({ error: 'forbidden' }, { status: 403 });
}
```
and in the submit route `if (!session || !isSetuManager(session) || !session.fid) → 401`. Use the `isAdmin`/`isSetuManager` helpers, never `session.role === 'admin'` (multi-role `extraRoles` makes strict equality silently wrong - existing repo rule).

## MAJOR-2 - No Firestore composite indexes are identified; both read paths will 500

**Task:** Tasks 5, 6 (and the missing runbook §5 entry in Task 4 Step 7).

The plan does not mention `firestore.indexes.json` once. Two queries are implied and neither is servable by single-field indexes:

- **The card** (Task 5) must read a family's pledges: `where('fid','==',fid).orderBy('submittedAt','desc')` → needs `pledges (fid ASC, submittedAt DESC)`. This is the exact shape of the existing `getDonations` query, which documents its index at `apps/portal/src/features/setu/donations/get-donations.ts:22-23` and has the matching entry in `firestore.indexes.json:73-80`.
- **The sweep** (Task 6) must find stale pendings: `where('status','==','pending').where('submittedAt','<',cutoff)` → needs `pledges (status ASC, submittedAt ASC)`.

Per CLAUDE.md discipline 8, a 3-field index does not serve a 2-field query shape, and fake-firestore is index-blind so the plan's unit tests will pass either way. This is precisely the `/family/seva` 500 pattern.

**Fix.** Add both entries to `firestore.indexes.json`, deploy to UAT only (`--project chinmaya-setu-uat`, never `--force`, never prod), and add them to runbook §5. Add the index audit as an explicit step in Task 5 and Task 6.

## MAJOR-3 - The `enabled` kill switch is designed but never wired, and there is no feature flag

**Task:** Tasks 2, 4, 5.

Spec §4.4 specifies `app_config/pledge.enabled` as a "kill switch". No task in the plan reads it. Task 4 Step 3 validates only the amount; Task 5 places the card unconditionally.

Separately, repo discipline 5 (CLAUDE.md, "non-negotiable") is: *"All risky features gated through `apps/portal/src/lib/flags.ts`. No hardcoded booleans."* Every comparable feature has one - `setuDonations`, `setuSeva`, `setuPrasad`, `setuDisclaimers`. The most sensitive feature in the system has none. If bank collection has to be stopped at 9pm on a Sunday, there is currently no way to do it except a code deploy.

Add `NEXT_PUBLIC_FEATURE_SETU_PLEDGE` to `turbo.json`'s build `env` array (alongside the other `NEXT_PUBLIC_FEATURE_*` entries) or Vercel builds will not see it. Gate the route and the card:

## MAJOR-4 - The backstop sweep is a manual CLI script, so it has the failure mode it exists to prevent

**Task:** Task 6.

Spec §6.4 says *"A **scheduled** sweep purges `pledge_secrets` for any pledge still pending after 90 days"*. The plan builds `apps/portal/scripts/purge-stale-pledge-secrets.ts` with `--dry-run` **default** and adds it to "runbook §10... as a recurring operational step" (Task 6 Step 5).

The sweep exists because a human forgets to confirm a pledge. It is then guarded by a human remembering to run a script - and, because dry-run is the default, remembering to pass `--commit`. Real bank account numbers persist for exactly as long as someone forgets twice.

The repo already has the right pattern: three Vercel Crons in `vercel.ts`, each self-authenticating on `CRON_SECRET` via `verifyCronAuth`, each allowlisted in `PUBLIC_ROUTES` (`public-routes.ts:84-87`).

**Fix.** Ship the shared `purgeStalePledgeSecrets()` function (keep the script as the manual/dry-run tool) and add a cron route:

```ts
// vercel.ts
{ path: '/api/cron/purge-stale-pledge-secrets', schedule: '0 5 * * *' },
```
```ts
// apps/portal/src/app/api/cron/purge-stale-pledge-secrets/route.ts
export async function GET(req: Request) {
  if (!verifyCronAuth(req)) return NextResponse.json({ error: 'unauthorized' }, { status: 401 });
  const { purged } = await purgeStalePledgeSecrets({ olderThanDays: 90, commit: true });
  return NextResponse.json({ ok: true, purged }); // count only, never a pid list with details
}
```
Add `/api/cron/purge-stale-pledge-secrets` to `PUBLIC_ROUTES` **in the same commit** - the file's own comment at `public-routes.ts:82-83` warns that a cron whose route is missing there silently 401s forever.

While you are there: build spec §6.4's **stale-pledge report** too. The plan's Self-Review explicitly flags it as deferred and asks the reviewer to confirm. **Do not defer it.** It is a one-line count in the existing weekly reminder cron, and without it the first signal that staff forgot a pledge is a silent purge 90 days later - which, per the plan's own framing, is "the likeliest failure mode, not the rarest". A pending count in the existing Sunday reminder email costs nothing.

## MAJOR-5 - After the sweep, a pledge can still be confirmed `active` with details that no longer exist

**Task:** Tasks 3 and 6.

The sweep deletes `pledge_secrets/{pid}` and deliberately leaves `pledges/{pid}` at `status: 'pending'` (Task 6's second test pins this). Nothing then prevents `confirmPledge` from flipping that pledge to `active` - `txn.delete` on an already-absent doc is a silent no-op, so the confirm succeeds, the family gets an "your monthly gift is active" email, and no PAD was ever set up because the details were destroyed 60 days earlier.

The family also sits on "we're setting up your monthly gift" indefinitely in the meantime, with no path back to the ask (spec §5.1: `cancelled` returns to the ask; `pending` does not).

**Fix.** Make the purge visible in the non-sensitive record and make confirm fail closed on it:

```ts
// purge sweep — same transaction as the delete
txn.delete(db.collection('pledge_secrets').doc(pid));
txn.update(db.collection('pledges').doc(pid), {
  status: 'cancelled',
  cancelledAt: FieldValue.serverTimestamp(),
  cancelReason: 'stale-secret-purged',
  secretPurgedAt: FieldValue.serverTimestamp(),
});
```
and in `confirmPledge`, inside the transaction after reading the pledge:
```ts
if (data.secretPurgedAt) throw new Error('pledge-secret-purged'); // → 409, staff must ask the family to resubmit
```
Setting `cancelled` also returns the card to the ask, which is the correct family-facing outcome and costs nothing.

## MAJOR-6 - No duplicate-submission guard: one family can hold N live secrets

**Task:** Tasks 3, 4.

Nothing in `submitPledge` or the route rejects a second submission while a `pending` one exists. A double-clicked submit button, a retried request on a flaky connection, or a family that "tries again" because verification is manual and slow, each mints a new `pledges/{pid}` **and a new `pledge_secrets/{pid}` holding real bank data**. The admin confirms one; the rest sit for 90 days. This is also an N=2 hazard for Task 5's card (which the plan does test) but the security half - N live secrets - is untested.

There is no rate limit on `POST /api/pledges` either. The repo has an established limiter (`features/check-in/shared/otp-rate-limit`); an authenticated manager spamming submits is low-probability, but the duplicate guard is the real fix and it is trivial.

**Fix.** Inside the submit transaction, read first:

```ts
const existing = await txn.get(
  db.collection('pledges').where('fid', '==', fid).where('status', '==', 'pending').limit(1),
);
if (!existing.empty) throw new Error('pledge-already-pending'); // → 409
```
(Note this adds a third index shape: `pledges (fid ASC, status ASC)`. Audit it per MAJOR-2.) Client-side, disable the submit button on first click - necessary but not sufficient on its own.

## MAJOR-7 - Two of the three headline security tests do not test what they claim

**Task:** Task 4, Step 1.

**(a) The "no route returns bank details to any role" test is vacuous.** It calls `GET_ANY_PLEDGE_ROUTE(pid, role)` - but the plan builds **no GET route at all**. The test therefore asserts that a 404 body contains no bank fields. It will pass forever, including after someone adds a leaky GET route, because the helper is undefined and will just be stubbed to whatever exists. This is the single most important test in the plan (spec §10.2 calls it "the most important one here") and as written it is a no-op.

**Fix.** Make it enumerate the real surface, so adding a route is what makes it fail:

```ts
// Enumerate every route module under src/app/api at test time, hit each with
// each role, and assert the response body never contains a bank field name or
// the seeded account number. A new route is automatically covered.
const routes = await globby('src/app/api/**/route.ts');
for (const r of routes) { /* GET + POST with each role, scan body */ }
```
Plus a targeted assertion on the actual family read paths named in spec §10.2 - `getCurrentFamily`, `GET /api/setu/family`, `GET /api/setu/dashboard`, `GET /api/welcome/families`, the roster CSV, and the reports CSVs - seeded with a family that has a pending pledge. (These are safe by construction today: `pledge_secrets` is top-level and every `collectionGroup()` in the repo targets only `donations`/`enrollments`/`invites`/`members`, with `listCollections()` never called. But that is a property that must be *pinned*, not assumed - it is one careless `collectionGroup('pledge_secrets')` away from being false.)

**(b) The "family cannot submit for another family" test asserts the wrong thing.**

```ts
const res = await POST_SUBMIT({ ...VALID }, { ...MANAGER, 'x-portal-fid': 'CMT-OTHER' });
expect(written.fid).toBe('CMT-OTHER');   // always the SESSION fid, never a body field
```

This sets the *session* fid to `CMT-OTHER` and asserts the write used `CMT-OTHER`. It proves nothing - it would pass on an implementation that reads fid from the body too. The test it should be:

```ts
const res = await POST_SUBMIT(
  { ...VALID, fid: 'CMT-OTHER' },                 // body attempts a different family
  { ...MANAGER, 'x-portal-fid': 'CMT-A' },        // session says CMT-A
);
expect(res.status).toBe(200);
expect((await lastPledge()).fid).toBe('CMT-A');   // session wins
```
And `SubmitPledgeSchema` should use `.strict()` so an unexpected `fid` key is a 400 rather than silently ignored.

**(c) Minor, same block:** `expect((await POST_CONFIRM(pid, WELCOME)).status).toBe(403)`. The middleware layer denies with **401** (`middleware.ts:165`), not 403. Only a handler-level check (MAJOR-1) produces a 403. Pick one and make the test match the layer it is exercising.

## MAJOR-8 - No admin list endpoint, so the confirm workflow pushes staff into the Firestore console

**Task:** Task 4.

Confirm is `POST /api/admin/pledges/[pid]/confirm`. Nothing in the plan tells an admin what `[pid]` is. There is no admin list route, no admin page (spec §2: "An admin UI may follow later"), and `pid` never appears in the family-facing UI in a form staff can see.

The only way to obtain a pid is to open the Firestore console and browse the `pledges` collection - which sits one click away from `pledge_secrets`, in a console where the audit trail is Google's, not the app's. The design's entire premise is that no human ever browses this data. The workflow as specified guarantees they will, every single time.

**Fix.** Ship a minimal read-only list in Task 4 (it is ~30 lines and reads only the non-sensitive collection):

```ts
// GET /api/admin/pledges?status=pending  → admin-only via the existing /api/admin/ rule
// Returns [{ pid, fid, familyName, monthlyAmount, submittedAt }] — PledgeDoc fields only.
// Explicitly never touches pledge_secrets.
```
Same for the accounting hand-off: the export script (Task 6) should print the pid alongside each row so confirm is a copy-paste, never a console browse.

## MAJOR-9 - The export script's file handling and the accounting hand-off are undefined - and that is where the data actually leaves

**Task:** Task 6, Steps 3 and 5.

`export-pledge-details.ts` "writes the decrypted rows to a local file". Unspecified: where, with what permissions, whether it prints to stdout, whether it can land in the repo, and how it gets to accounting. Spec O6 owns the last part and is unassigned.

Concretely:
- **Repo pollution.** `.gitignore` has no pattern that would catch a decrypted export. A default `--out ./pledges.csv` puts plaintext bank details one `git add -A` away from a public-ish repo. (The repo does gitignore `.rtdb-snapshot`, so the pattern of protecting sensitive local data exists - it just has not been applied here.)
- **World-readable.** `writeFileSync` defaults to mode `0666 & ~umask` = `0644` on macOS. Every process on the machine can read it.
- **Terminal scrollback / CI logs.** If the script also prints rows (the existing scripts all log progress), the details land in scrollback, in `~/.zsh_history`-adjacent tooling, and in any agent transcript.
- **The hand-off.** Spec §8's proudest row is *"Email interception / logging — **Nothing sensitive is ever emailed.**"* That claim is only true of the portal. If the operator then emails the CSV to accounting, every control in this design is bypassed by the last mile, and there is no record of it.

**Fix (all cheap, all in Task 6):**
```ts
// Refuse to write anywhere but an explicit absolute path outside the repo.
if (!path.isAbsolute(out) || out.startsWith(repoRoot)) {
  throw new Error('[pledges] --out must be an absolute path outside the repository');
}
writeFileSync(out, csv, { mode: 0o600 });
// Never print a row. Print only: "wrote N rows to <path>".
```
- Reuse `apps/portal/src/lib/csv.ts`'s `csvCell` so the export inherits the repo's formula-injection neutralization (`lib/csv.ts:5`) - bank fields are digits so the risk is low, but there is no reason to hand-roll a second encoder.
- Add `*.pledge-export.csv` and `/pledge-export*` to `.gitignore` as belt-and-braces.
- **Write O6's answer into the runbook before launch, not after**: named recipient, transmitted via a channel with at-rest encryption and a retention limit (a password-protected archive handed over in person, or the bank's own secure portal - *not* email, *not* Slack, *not* Drive), and `shred`/`rm -P` on the local copy immediately after, in the same documented step. This is the highest-residual-risk part of the whole feature and it currently has no owner and no words.

## MAJOR-10 - No record that the family authorized the pre-authorized debit

**Task:** Tasks 2, 3, 5.

A PAD in Canada requires a payor's PAD agreement (Payments Canada Rule H1) containing specified elements, and the payor must be able to prove what they agreed to. The plan collects four bank fields and an amount. It stores no agreement text, no version, no timestamp of acceptance, and no acknowledgement checkbox. If a family later disputes a debit, there is nothing to show; and accounting's own processor will very likely ask for it before setting up the first PAD.

This is not a theoretical compliance point - the repo already has exactly the right pattern for it. `app_config/disclaimers` stores versioned content and the family's acceptance is recorded against that version (`packages/shared-domain/src/setu/schemas/disclaimers.ts`).

**Fix.** Put the agreement in the **non-sensitive** `pledges` doc, where it survives the purge (which is the whole point - the authorization must outlive the bank details):

```ts
// PledgeDoc, additional fields
padAgreementVersion: number;      // from app_config/pledge.padAgreementVersion
padAgreementAcceptedAt: Date;
padAgreementText: string;         // snapshot of exactly what was shown, so a later edit can't rewrite history
```
Render the agreement text above the submit button from `app_config/pledge` (admin-editable, per the no-external-CMS rule) with a required "I authorize Chinmaya Mission Toronto to debit my account..." checkbox, and reject the submit server-side if `padAgreementVersion` does not match the current config. Also decide and document the family's cancellation route now - v1 is read-only by decision (spec §2), which is fine, but the agreement text has to tell the family how to stop it.

# MINOR

1. **`keyVersion` is written but never read - rotation is not actually possible as written.** `decryptBankDetails` (Task 1 Step 3) calls `key()`, which always returns the single current `PLEDGE_ENCRYPTION_KEY`, and ignores `payload.keyVersion` entirely. Spec §4.3's *"`keyVersion` is stored so a future key rotation can decrypt old records"* is therefore false. Fix: `function key(version = KEY_VERSION)` reading `process.env[\`PLEDGE_ENCRYPTION_KEY_V${version}\`] ?? process.env.PLEDGE_ENCRYPTION_KEY`, and `decrypt` passes `payload.keyVersion`. Add a test that a v1 payload still decrypts after `KEY_VERSION` becomes 2.

2. **No AAD binding the ciphertext to its pledge.** GCM supports additional authenticated data at no cost. Without it, anyone with Firestore write access can move `pledge_secrets/A`'s payload to `pledge_secrets/B` and it decrypts cleanly - family B's pledge now carries family A's account. Fix: `cipher.setAAD(Buffer.from(pid, 'utf8'))` on both sides, `pid` passed into `encryptBankDetails`/`decryptBankDetails`. Add a test that a payload encrypted for pid A fails to decrypt under pid B.

3. **`PLEDGE_ENCRYPTION_KEY` is spec'd for "Vercel Production only" (§4.3) but Task 7 runs the E2E against deployed UAT.** The submit will throw `PLEDGE_ENCRYPTION_KEY is required` on `cmt-setu.vercel.app`. Generate a **separate** UAT key (never the prod one - UAT data has looser handling) and set it on Preview/UAT. Use `vercel env add --value` (stdin is silently ignored for agents) and verify with `vercel env pull`.

4. **`decryptBankDetails` returns an unvalidated `JSON.parse(...) as BankDetails`.** GCM guarantees the bytes are authentic, not that they are the right shape. Run the result through a Zod `BankDetailsSchema.parse` so a partial/legacy payload fails loudly at the export rather than producing a CSV row with `undefined` in the account column.

5. **Amount validation needs bounds.** `z.number()` accepts `Infinity` and non-integers. Use `z.number().int().min(cfg.minMonthlyAmount).max(10_000)`. An unbounded amount is not a data breach but it is a support call and a bad audit row.

6. **`accountNumber` needs a max length.** `/^\d+$/` with no cap lets a client send a megabyte of digits, which encrypts fine and then blows the 1 MB Firestore document limit at write time (or just wastes storage). Canadian account numbers are 7-12 digits: `z.string().regex(/^\d{7,12}$/)`.

7. **`bankNumber` is redundant with `institutionNumber`** - in Canada they are the same three-digit value; there is no separate "bank number". Collecting it invites a family to type something else, gives accounting a fourth field to reconcile, and violates data minimization for no benefit. Resolve O7 by dropping it: institution (3 digits), transit (5 digits), account (7-12 digits) is the complete set. Fewer sensitive fields is strictly better here.

8. **`SubmitPledgeSchema` should be `.strict()`** so unexpected keys (a body-supplied `fid`, `status`, or `pid`) 400 rather than being silently dropped. See MAJOR-7(b).

9. **`pid` generation is unspecified.** Use `db.collection('pledges').doc().id`. Do **not** derive it from a count of existing pledges - the repo has a data-loss incident from exactly that (`nextMemberMid`, 2026-07-19: count+1 collided on a numbering gap and `txn.set` silently overwrote a real member).

10. **`pledges` and `pledge_secrets` are missing from the test-cleanup sweeps.** `apps/portal/src/__tests__/e2e/helpers/firestore.ts` `cleanupTestData()` sweeps `families`/`members`/`invites`/`contactKeys`/`donationPeriods`, and `apps/portal/scripts/wipe-uat-leaks.ts` sweeps `families`/`contactKeys`/auth users. Neither knows about the new collections, so Task 7's E2E leaves pledge secrets in UAT indefinitely. Add both collections to both sweeps in Task 7, and mark E2E docs with `_test: true` like the rest.

11. **Idempotent double-confirm re-sends the activation email.** Task 3's idempotency test correctly pins one audit row, but `confirmPledge` returns `{fid, monthlyAmount, email}` unconditionally and Task 4 Step 4 sends on that. Return `{ alreadyActive: true }` on the no-op path and skip the send.

12. **Verify `MOBILE_CORS_ORIGINS` is empty in production.** `middleware.ts:25-37` applies `access-control-allow-credentials: true` to every `/api/*` path including `/api/pledges`. A stale dev origin (`http://localhost:8081` per `apps/portal/docs/mobile-api-integration.md:152`) left in the prod env would let a page on that origin submit bank details with the family's cookies. It is currently unset per the mobile spec - confirm, and add "MOBILE_CORS_ORIGINS is unset in Production" to the runbook launch checks.

13. **Spec §10.7 ("a pending pledge counts as payment nowhere") has no verification task.** It is true by construction today - nothing reads `pledges` - but the Self-Review claims §10.1-10.7 are all covered by Tasks 1-7 and §10.7 is not. Add one assertion to Task 7: seed a pending pledge, then assert the payment chip, `/welcome/roster` status, enrollment confirmation, and the enrollment report are byte-identical to the no-pledge baseline.

14. **Two small factual slips.** (a) Task 6 Step 3 says "`--dry-run` default" is a "repo script convention"; existing scripts default to *writing* (`migrate-legacy-families.ts:31` `dryRun: false`). Dry-run-by-default is the right choice here - just do not call it the existing convention, because a reviewer checking the claim will find the opposite. (b) Spec §3 cites `SECURITY_REVIEW_2026-07-22.md:1282`; the line is `:1284`. (c) Spec §7.1 calls the interface `Sender`; it is `ResolvedSender` (`resolve-sender.ts:6`).

## Answers to the six questions asked

**1. Can bank details leak anywhere?**
Through the HTTP surface: no, the architecture is sound - `pledge_secrets` is top-level, no `collectionGroup()` in the repo targets it, `listCollections()` is never called, and no route reads it. Through **observability: yes, today, by default** (CRITICAL-1). Through the **database layer: unknown and unmanaged** (CRITICAL-2). Through the **accounting hand-off: yes, and it is undefined** (MAJOR-9). The plan's claim is true of exactly the one surface it examined.

**2. canAccessRoute.** The `:311-313` landmine claim is exactly right, the `/api/pledges` placement is correct, `/api/admin/pledges/*` correctly lands on the admin-only `:75` rule with none of the three welcome-team exceptions matching, `middleware.ts:197` covers both paths, and `x-portal-*` headers are set-or-deleted so forgery fails. The gap is not in the rule - it is that the rule is the *only* gate (MAJOR-1).

**3. The crypto.** IV is 12 random bytes per call, never reused. authTag is set before `final()`, so tampering and wrong keys both throw - genuinely fail-closed. Key is read per call, length-checked, never re-exported. Real gaps: `keyVersion` is ignored on decrypt so rotation does not work (MINOR-1), no AAD binding to pid (MINOR-2), unvalidated `JSON.parse` on output (MINOR-4), and the plaintext `details` object is capturable by Sentry's stack-frame variables (CRITICAL-1).

**4. The purge.** Atomicity holds *as written* - P1's `writeAuditLog(txn, db, entry)` genuinely takes the caller transaction (verified in the P1 plan), so status flip + secret delete + audit row commit together or not at all. Concurrent confirms serialize correctly **provided the implementation does `txn.get(pledgeRef)` before writing** - the plan never says so, and without that read Firestore has nothing to detect contention on. Make it explicit in Task 3 Step 3. `txn.delete` on an absent doc is a no-op, so retry is safe. The real hole is not atomicity: it is that a pledge can reach `active` after its secret was swept (MAJOR-5).

**5. The backstop sweep.** It covers abandoned pledges only if someone runs it, twice-remembered (script + `--commit`), forever - which is the same human-forgetfulness failure it was built to catch (MAJOR-4). Secrets also outlive it in the duplicate-submission case if only the confirmed pledge is considered (MAJOR-6). Make it a cron; build the 14-day stale report the plan proposes to defer.

**6. What the plan misses.** Ranked by what I would actually fix first: Sentry egress, Firestore rules, handler-level role checks, the missing indexes, the kill switch/flag, the sweep-as-cron, the sweep/confirm interaction, the duplicate guard, the two broken security tests, the missing admin list (which forces console browsing), the export file handling and hand-off, and the PAD authorization record.
