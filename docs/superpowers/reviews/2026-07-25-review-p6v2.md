# Review: P6 v2 - Dormant-Family Skip & Unknown-Centre Prompt

Plan: `docs/superpowers/plans/2026-07-25-launch-p6-migration-dormant-and-centre-v2.md`
Spec: `docs/superpowers/specs/2026-07-24-aug-3-launch-batch-design.md` §1.9a / §1.9b / §1.9c
Prior review (v1): `docs/superpowers/reviews/2026-07-25-review-p6.md`
Reviewed against real code at HEAD `b1395e0`. Defects only.

**Verdict: REQUEST CHANGES. 2 critical, 6 major, 8 minor.**

v2 fixed almost every v1 finding correctly (see the calibration list). But in fixing
C1 it introduced the same failure shape one layer down: the plan now depends on a
parser signal, `locationDefaulted`, that **does not exist in the codebase and that no
task in this plan creates** - while calling it "Task 1's *existing*" field. The
centre-prompt half is inert again, for a different reason. The second critical is the
Save-button gate: `centreReady` is used in Task 6 Step 4 and never defined, and the one
sentence that does define it (Step 6) deadlocks Save for every family that is *not*
flagged - which is 100% of the launch population.

## CRITICAL

### C1 - `locationDefaulted` does not exist and no task creates it; the flag is never written

**Task 1 Step 3 + Task 2 Step 5.**

**Claim (Task 1 Step 3):** "Add `dormant: boolean` to `LegacyFamilyForMigration` ...
alongside Task 1's **existing** `locationDefaulted`."
**Claim (Task 2 Step 5):** "**Write it during migration** - `lazy-migrate.ts:193-201`
sets it `true` when `locationDefaulted` is true."

**Truth:** `locationDefaulted` does not exist anywhere in `apps/` or `packages/`.

```
$ grep -rn "locationDefaulted" --include="*.ts" --include="*.tsx" apps packages
(no matches)
$ grep -rn "mapLocationDetailed" apps packages
(no matches - it appears only in the v1 plan and the v1 review)
```

Confirmed at each site:
- `apps/portal/src/features/setu/registration/legacy-parser.ts:112-116` -
  `mapLocation(value)` returns a bare `LegacyLocation`; it reports nothing about
  having fallen back.
  ```ts
  function mapLocation(value: unknown): LegacyLocation {
    const s = clean(value);
    if (s && (VALID_LOCATIONS as readonly string[]).includes(s)) return s as LegacyLocation;
    return 'Brampton';
  }
  ```
- `legacy-parser.ts:83-93` - `LegacyFamilyForMigration` has 9 fields; no
  `locationDefaulted`, no `dormant`.
- `legacy-parser.ts:224` - `location: mapLocation(first.center),` is the only call site.
- `lazy-migrate.ts:193-201` - the family `txn.set` writes 7 keys; no flag.

The parser change is a **spec requirement the plan dropped**, not an inference:
spec §1.9c Part 3 item 2 reads "**Parser** - `mapLocation` reports whether it fell back
to the default; `lazy-migrate` persists `locationNeedsConfirmation: true` in that case."
v1 had a task for it (v1 plan `:111-124`, `mapLocationDetailed` + `locationDefaulted`).
v2's Task 1 is entirely about dormancy and adds only `dormant`; no other task touches
`mapLocation`.

**Consequence:** `locationNeedsConfirmation` is never written `true` by any code path.
The schema field, both gate edits (Task 5), all four form edits (Task 6) and the PATCH
clear (Task 4) all fire on a value that is permanently absent. §1.9c ships doing
nothing - the exact outcome v1's C1 identified, relocated from the read path to the
write path. Task 2 Step 1's unmocked `getFamilyByFid` round-trip test **seeds the doc
directly** (`seedFamilyDoc({ fid: 'CMT-A', locationNeedsConfirmation: true })`), so it
passes green without ever exercising the writer. Nothing in the plan's test list
catches this.

**Fix:** restore the parser task. Add to Task 1 (or a new task before Task 2):
1. `mapLocationDetailed(value): { location: LegacyLocation; defaulted: boolean }` in
   `legacy-parser.ts`, with `mapLocation` kept as a thin wrapper.
2. `locationDefaulted: boolean` on `LegacyFamilyForMigration` (`:83-93`), set at `:224`.
3. A test asserting `locationDefaulted === true` for `center: 'NULL' | '' | missing | 'ALL'`
   and `false` for `'Brampton'`.
4. Task 2 Step 5 then has something to read. Add a `lazyMigrateLegacyFamily` test that
   asserts the written family doc carries `locationNeedsConfirmation: true` for a
   defaulted-centre legacy family and **omits it** otherwise - the test that would have
   caught this.

### C2 - `centreReady` is undefined; the only definition given blocks Save for every unflagged manager

**Task 6 Step 4 + Step 6.**

**Claim (Step 4):** "Add `centreReady` to `allReady` (`:288-295`)".
**Claim (Step 6):** "`centreReady` requires a non-empty explicit choice."

That is the whole specification. Taken literally - `centreReady = centre !== ''` - it
blocks the Save button for **every manager who is not flagged**, and the selector that
would satisfy it is specified to render only when the flag is set (Step 6, and spec
§1.9c Part 3 item 4: "a centre selector, shown only when the flag is set"). A manager
with no selector and an unsatisfiable `centreReady` has no way forward at all.

`allReady` is a hard block, not a hint - `complete-profile-form.tsx:312-324`:
```ts
if (!allReady) {
  setShowErrors(true);
  ...
  toast.error('Please fill the highlighted fields to continue.');
  return;               // no PATCH, no navigation
}
```

The existing sibling shows the escape hatch the plan omits -
`complete-profile-form.tsx:274-282`:
```ts
const addressReady = useMemo(() => {
  if (!data?.isManager) return true;      // <- the vacuous-true guard
  return street.trim().length > 0 && ...;
}, [...]);
```
`centreReady` needs the same shape *plus* a flag clause:
`if (!data?.isManager || data.family.locationNeedsConfirmation !== true) return true;`
The plan never says this.

**Blast radius is 100% of the launch population, not an edge case.**
`lazy-migrate.ts:132-136` (adults) and `:183-189` (children) write
`foodAllergies: null`, `volunteeringSkills: []`, `birthMonthYear: null`, and
`gender: 'PreferNotToSay'` for any legacy row without M/F. Per
`packages/shared-domain/src/setu/member-required-fields.ts:34-42` and `:86` (which
treats `PreferNotToSay` as MISSING), **every migrated member is incomplete by
construction** - the spec says so itself at §1.9b. So every one of the ~568
bulk-migrated managers is routed to `/complete-profile` at first sign-in, hits the
Save button, and - under the literal reading - cannot leave.

Task 6 Step 1's test list is: "a members-complete, address-complete, centre-unknown
manager **stays on the form**; the selector starts unselected; Save sends `location`;
the flag clears." There is **no** negative test for an unflagged manager, so this would
ship green. (Contrast Task 5 Step 1, which does have the negative cases, and v1's Task 4
Step 1 fourth test, which the v1 review specifically praised.)

**Fix:** write `centreReady` out in full in Step 4, and add the missing test to Step 1:
```ts
const centreNeeded = !!data?.isManager && data.family.locationNeedsConfirmation === true;
const centreReady = !centreNeeded || centre.trim().length > 0;
```
Tests to add: (a) an unflagged manager with one incomplete member can still Save;
(b) a non-manager can still Save; (c) a flagged manager cannot Save until they pick.
Render the selector iff `centreNeeded`, so the rendered control and the gate agree.

**Global Constraints + Task 2 Files + Task 2 Step 4.**

**Claim:** "`get-session-family.ts:22` - **the same map** feeds `GET /api/setu/family`" and

**Truth:** `apps/portal/src/features/setu/members/get-session-family.ts:22` is

a delegation, not a map. `:25-30` spreads `cached.family` through unchanged. There is

implementer to a file with no target and no diff.

**The second construction site the plan misses** is
`apps/portal/src/features/setu/search/get-family-for-welcome.ts:41-50`:
```ts
  const family: FamilyDoc = {
    fid: familyData.fid,

    name: familyData.name,
```

This backs `/welcome/family/[fid]`, the welcome-team detail page. It already drops

Full audit of `FamilyDoc` object construction in non-test source (`grep -rn ": FamilyDoc = {"`):
exactly two - `get-family-by-fid.ts:26` and `get-family-for-welcome.ts:41`. No third.

**Fix:** replace the `get-session-family.ts:22` bullet with `get-family-for-welcome.ts:41-50`,
and say explicitly that `get-session-family` / `get-current-family` need no change because
they delegate.

### M2 - Task 3 Step 4 repeats, verbatim, the unimplementability Task 1 diagnosed

**Task 3 Step 4.** "Exclude dormant fids from `legacyFids` and report them as a separate
`skippedDormant` count."

`reconcile-migration.ts:13` gets its fids from the same function Task 1 spends a
paragraph rejecting:
```ts
const [legacy, setuLegacyFids] = await Promise.all([listAllFamilies(), listSetuLegacyFids()]);
```
`listAllFamilies()` (`features/check-in/shared/rtdb/family-lookup.ts:212`) returns
`Family[]` - `packages/shared-domain/src/check-in/family.ts:31-38` is
`{ fid, name, contacts, paymentStatus, students, notes? }`, **no `center`**, and `level`
survives only as `Student.level`, blanked for adults and lossily normalized at
`family-lookup.ts:138-139` (only the exact uppercase `'NULL'`). Task 1's own words:
"Dormancy is not reconstructible from it."

The step gives no mechanism. The obvious-but-wrong one (reuse the `Family` shape) yields
a dormant set that **disagrees with the migration's own skip set**, producing a health
indicator that is confidently wrong rather than merely red. The right one - read
`/roster` in `reconcile-migration.ts` and group by fid, or persist the skipped fids from
the migration run - is a different design decision that must be made in the plan, not by
the implementer at 2am.

Also unstated: `MigrationStatusResponse` lives in `@cmt/shared-domain/setu` and is
returned by `GET /api/welcome/families/migration-status` (`route.ts:14`), so adding
`skippedDormant` is a response-shape change - Step 4 says "if `MigrationStatusResponse`
changes shape, add a changelog entry", which under-commits: it *will* change shape.

**Fix:** name the mechanism. Cheapest correct option: have the migration script write
the skipped fids to a Firestore doc (or reuse the CSV) and have `getMigrationStatus`
subtract that set; otherwise state explicitly that `reconcile-migration.ts` reads
`/roster` directly and shares one exported dormancy predicate with the parser.

### M4 - Task 7's dormant E2E asserts an outcome that cannot happen

**Task 7 Step 2, third bullet:** "a dormant family signs in and is lazily migrated
**with a real centre**".

A dormant family is defined by Task 1 as one where **every row has no centre and no
level**. Measured against `apps/portal/.rtdb-snapshot/roster.json` (2,543 rows, 867
families, `capturedAt: 2026-06-10`): all 299 dormant families have no usable `center` on
any row. `mapLocation(first.center)` (`legacy-parser.ts:112-116`) therefore returns
`'Brampton'` for every one of them. A dormant family **cannot** lazily migrate with a
real centre - it migrates as Brampton and (per §1.9c, once C1 is fixed) carries
`locationNeedsConfirmation: true` and must be routed to `/complete-profile`.

Written as-is the E2E asserts the wrong post-condition and would pass while the
centre-prompt half is broken - the third instance in this plan of a green test over a
dead feature.

**Fix:** "a dormant family signs in → is lazily migrated → lands on `/complete-profile`
→ is asked for its centre → picks one → the flag clears." That is the *actual* primary
path for §1.9c (see M5 below), and the plan currently has no E2E for it.

### M5 - After the dormant skip, only 2 of 867 bulk-migrated families carry the flag; the plan never says so

**Measured facts section + Task 7 Step 4 (runbook).**

The plan presents "**299 of 867 families (34%)** have no usable centre on any row and
migrate as Brampton" as the population for §1.9c, and its goal line is "ask the families
whose centre we defaulted to pick their real one". But those same 299 are precisely the
set Task 3 **skips**. Reproduced against the snapshot:

```
dormant (no centre AND no level on any row) : 299
would default to Brampton (mapLocation)     : 301
overlap                                     : 299
defaulted but NOT dormant                   : 2   -> legacy fids 1016, 1367 (center 'ALL')
dormant but NOT defaulted                   : 0
```

So at cutover the bulk migration writes `locationNeedsConfirmation: true` on **exactly 2
families**. The other 299 get it only when they individually lazy-migrate at first
sign-in. That is consistent with spec §1.9c and is almost certainly the intent - but the
plan states it nowhere, and two concrete artefacts depend on knowing it:
- Task 7 Step 4's runbook bullet lists "the expected `skippedDormant` count" but not the
  expected `locationNeedsConfirmation` count, so the first person who queries the field
  post-migration sees 2 and cannot tell success from failure.
- The UAT verification (Task 7 Steps 1-2) seeds a flagged family by hand, so it never
  exercises the real production path (dormant → sign-in → lazy migrate → flagged →
  prompted). See M4.

**Fix:** state the interaction in the Measured facts section ("299 of the 301 defaulted
families are skipped by Task 3; the flag reaches them on the lazy path, not the bulk
one; bulk-migration yields exactly 2 flagged families - legacy fids 1016 and 1367"), put
both expected counts in the runbook, and make the lazy path the primary E2E.

### M6 - No feature flag on the highest-blast-radius change in the batch

**Tasks 5 and 6.** Neither adds a flag. `apps/portal/src/lib/flags.ts` is the mechanism
CLAUDE.md discipline 5 mandates ("All risky features gated through
`apps/portal/src/lib/flags.ts`. No hardcoded booleans."), and `DisclaimerGate` is the
in-file precedent: `app/family/layout.tsx:68` opens with
`if (!flags.setuDisclaimers) return null;`.

Task 5 adds a **new redirect condition** to two gates that run on every `/family/*`
render, and Task 6 changes the **only** screen 100% of families pass through at first
sign-in - three days before a cutover that sends ~867 families through it. The plan's own
Self-review says exactly that under "Known risk" and then ships no kill switch: if either
C2's deadlock or a mis-set flag reaches prod on launch Sunday, the only remedy is a code
deploy.

P4 v2 treats the identical situation as a v1 defect and fixes it - Task 8 Step 1: "**v1
added the gate unconditionally**, which violates discipline 5 and removes the kill
switch three days before launch - on a gate that redirects."

**Fix:** add `setuCentreConfirmation` to `flags.ts` (and `turbo.json`'s `env` array - see
the standing `feedback_turbo_env_passthroughs` rule), short-circuit both the gate clause
and the form's `centreNeeded` on it, default OFF, flip on after the UAT walkthrough.

validated on READ** ... Writing `null` or `''` fails validation on every subsequent read

but the stated mechanism does not exist and a future reader will act on it.
