## C2 - With prod rules un-shippable, `pledges` is client-writable in prod and the plan has no fallback

**Confidence: MEDIUM-HIGH.** Follows from C1.

The plan's premise (`:37`) is exactly right: *"Encryption makes a `pledge_secrets` leak survivable; it does nothing for `pledges`, where open rules would let a family flip their own pledge to `status: 'active'` - precisely the 'unverified money counted as real' risk the design claims to have closed."*

The standalone app's `'use client'` pages successfully read and write `family-check-ins`/`guest-families` in `715b8` today. That is only possible if the deployed prod ruleset permits authenticated (or open) client access to those paths. Since no ruleset is tracked in either repo, it was authored in the console, and the overwhelmingly likely shape is a blanket `allow read, write: if request.auth != null` or a test-mode `request.time <` clause - i.e. `pledges/**` and `pledge_secrets/**` will be **client-readable and client-writable in prod on day one**, by any family holding a Firebase session.

Plan Task 1 Step 4 (`:72-74`) frames the console check as informational - *"Record the answer in the runbook either way."* It is not informational. It decides whether P5 can ship to prod at all, and the plan has **no branch** for the answer it is going to get. Meanwhile spec §8 sells "Unverified money counted as real -> only a server-side staff action sets `active`" as a closed risk.

**Fix.** Before any pledge code lands:
1. Export the deployed `715b8` ruleset and commit it as `firestore.rules` (baseline first, tightening second).
2. Add the two P5 collections as explicit denies **on top of** whatever the door app needs - a targeted `match /pledges/{pid} { allow read, write: if false; }` and the same for `pledge_secrets` costs nothing and does not touch `family-check-ins`.
3. Make Task 6's `NEXT_PUBLIC_FEATURE_SETU_PLEDGE` flip in prod **blocked on** step 2, not just on the O4 key backup (plan `:248` currently gates it only on the key backup).

# MAJOR

## M1 - The backstop sweep cron is missing from `PUBLIC_ROUTES`, so it silently 401s forever

Task 10 Step 3 (`:323`): *"Implement as a Vercel Cron route, declared in `vercel.ts` beside the existing daily crons."* That is the whole instruction. It never mentions `PUBLIC_ROUTES`, and it never mentions `CRON_SECRET`.

`packages/shared-domain/src/auth/public-routes.ts:78-89` is unambiguous:

> *"EVERY path declared as a cron in vercel.ts MUST be listed here - a scheduled job whose route is missing here silently 401s."*

`canAccessRoute` has no `/api/cron/` clause, so an unlisted cron path falls to the default-deny at `can-access-route.ts:315`, and middleware denies at `middleware.ts:97-99` before the handler runs. Vercel Cron sends `Authorization: Bearer ${CRON_SECRET}`, which `verifyPortalIdToken` cannot decode (`middleware.ts:89-91`).

Consequence: the 90-day purge - the control that exists precisely because humans forget - never fires, silently, with a green `vercel.ts` entry as evidence that it does. Real bank account numbers are retained indefinitely. This is the failure the prior review's MAJOR-4 named and the v2 rebuild dropped the remedy for.

The opposite mistake is worse. `public-routes.ts:91-95` warns:

> *"Adding a route here without a self-authenticating handler would expose an unauthenticated endpoint with no enforcement."*

An unauthenticated `GET /api/cron/purge-stale-pledge-secrets` mass-deletes `pledge_secrets` and flips pledges to `cancelled`.

**Fix.** Task 10 Step 3 must say all three, in one commit: (a) add `'/api/cron/purge-stale-pledge-secrets'` to `PUBLIC_ROUTES`; (b) copy the `verifyCronAuth` timing-safe Bearer check verbatim from `apps/portal/src/app/api/cron/send-prasad-reminders/route.ts:5,17`; (c) add `{ path: ..., schedule: ... }` to `vercel.ts:4-11`. Add a test that the route 401s without the Bearer.

## M2 - The `keyVersion` fallback makes rotation silently destroy the only copy of the bank details

Task 2 Step 3 (`:116-119`):

```ts
const raw = process.env[`PLEDGE_ENCRYPTION_KEY_V${version}`] ?? process.env.PLEDGE_ENCRYPTION_KEY;
```

The `??` fallback is applied on **both** sides. Two failure modes, both silent:

1. **Bump `KEY_VERSION` to 2 without setting `PLEDGE_ENCRYPTION_KEY_V2`** -> new blobs are stamped `keyVersion: 2` but encrypted with the v1 key. Set `_V2` later (the natural next step) and every one of those blobs is permanently undecryptable.
2. **Rotate by replacing `PLEDGE_ENCRYPTION_KEY`** - the only variable named in spec §4.3, in Task 13 Step 1 (`:412`) and in Task 13 Step 6's runbook list (`:417`) - and every existing `keyVersion: 1` blob loses its key, because nothing told the operator to preserve the old value under `PLEDGE_ENCRYPTION_KEY_V1`.

`PLEDGE_ENCRYPTION_KEY_V*` appears **nowhere** outside that one snippet: not in Task 13 Step 1's Vercel env step, not in Task 13 Step 6's runbook list, not in `turbo.json` (Task 6 Step 1 adds only `NEXT_PUBLIC_FEATURE_SETU_PLEDGE`, even though spec §4.3 explicitly requires `PLEDGE_ENCRYPTION_KEY` in the passthrough array and `turbo.json:12-56` does list every other server secret including `AWS_SECRET_ACCESS_KEY` and `CRON_SECRET`).

Worse, the plan's own rotation test (`:100-103`) passes in a harness where both vars are set, so it certifies a rotation path that does not survive the real operator action. This is a "verified once, confidently asserted" defect in the same family as the four prior rebuilds.

Realistically: for any pledge still `pending`, the decrypted export is the **only** path to accounting and the secret is destroyed on confirm. Losing the key loses the money for those families until they resubmit.

**Fix.** Drop the `??`. Resolve keys from an explicit map and **throw** when a requested version is absent:
```ts
const KEYS: Record<number, string | undefined> = {
  1: process.env.PLEDGE_ENCRYPTION_KEY_V1 ?? process.env.PLEDGE_ENCRYPTION_KEY, // v1 legacy alias only
  2: process.env.PLEDGE_ENCRYPTION_KEY_V2,
};
function key(v: number) { const raw = KEYS[v]; if (!raw) throw new Error(`pledge key v${v} not configured`); ... }
```
Add the rotation runbook step ("set `_V{new}` first, keep `_V{old}` forever, never edit `PLEDGE_ENCRYPTION_KEY`") to Task 13 Step 6, and add `PLEDGE_ENCRYPTION_KEY` + `PLEDGE_ENCRYPTION_KEY_V*` to `turbo.json`'s `build.env`.

## M3 - `confirmPledge` guards the swept-secret path but not the cancelled path

Task 5 Step 3 (`:228-234`) specifies exactly two in-transaction guards: `txn.get(pledgeRef)` for contention, and `if (data.secretPurgedAt) throw new Error('pledge-secret-purged')`.

`secretPurgedAt` is written by exactly one thing: the Task 10 sweep (`:326-333`). The **cancel** path is different. Task 5's title is `confirmPledge` / `cancelPledge` and spec §6.3 says cancel sets `status='cancelled'` and deletes the secret - but the plan never says `cancelPledge` writes `secretPurgedAt`, and it never says `confirmPledge` rejects a non-`pending` status.

So: admin cancels pledge X (secret deleted, status `cancelled`), then confirms X - by a stale browser tab, a re-run of the copy-pasted `pid` from Task 8's list, or two staff working the same queue. `txn.delete` on the already-absent secret is a no-op, `secretPurgedAt` is unset, status flips to `active`, `writeAuditLog` records a clean confirm, and the family receives "your monthly gift is active" for a PAD that will never exist because the details are gone.

That is the identical end state the prior review's MAJOR-5 was written to close - re-entered through the cancel door instead of the sweep door.

**Fix.** In `confirmPledge`, after `txn.get(pledgeRef)`:
```ts
if (data.status === 'cancelled') throw new Error('pledge-cancelled');   // -> 409
if (data.status === 'active')    return { alreadyActive: true };
if (data.secretPurgedAt)         throw new Error('pledge-secret-purged'); // -> 409
```
and make `cancelPledge` set `secretPurgedAt` too, so the invariant is "no secret => `secretPurgedAt` is set", enforced in one place. Add the confirm-after-cancel case to Task 5 Step 1's test list.

## M4 - The activation email does not satisfy P3 v2's contract, and a send failure strands it permanently

Task 6 Step 5 (`:270`): *"Send the activation email via P3's `sendManagedEmail` with `name: 'pledge-activated'`, **outside** the confirm transaction... Skip on the `alreadyActive` path."*

P3 v2's actual signature (`2026-07-25-launch-p3-communications-v2.md:215-220`):
```ts
export async function sendManagedEmail(args: {
  name: ManagedEmailName; to: string; data: Record<string, unknown>;
  fallback: () => Promise<void>;                 // REQUIRED
}): Promise<void>
```

`'pledge-activated'` **is** in the union (`p3v2:212`) - that part is fine. Two things are not:

1. **`fallback` is required and P5 has nothing to put there.** Spec §7 is explicit: *"No email subject or body text is hardcoded in the codebase for this feature."* Every other managed name falls back to an existing in-code renderer; pledge has none by design. P5 never mentions the parameter. The executor writes `fallback: async () => {}`, and then P3 v2's "not configured" branch (`p3v2:228`, an **info** log, not an error) means: if Vaibhav's SES template or its `SES_TEMPLATE_*` env var is missing at launch, **every activation email silently does not send** and nothing surfaces it. Spec O5 and O8 are both still open, so that is the likely launch state.

2. **No error handling on the send.** P3 v2 pins that non-template SES failures **propagate** (`p3v2:235-238`) and a fallback throw propagates unchanged (`p3v2:240-246`). Being outside the transaction protects the Firestore write, but an uncaught throw makes `POST /api/admin/pledges/[pid]/confirm` return 500. The admin sees a failure and retries - and the retry hits Task 5's idempotent path, returns `{ alreadyActive: true }`, and **deliberately skips the send** (`:213-217`, `:270`). The email is now unsendable through the product, on a pledge whose bank details have already been destroyed. Spec §7.3 requires exactly this be handled: *"a failed email must be logged and surfaced, never allowed to undo that."*

**Fix.** Task 6 Step 5 must specify: the full `{ name, to, data, fallback }` call; a `fallback` that **throws or alarms** rather than no-ops (silent non-delivery on the most important transactional email in the feature is not an acceptable default); a `try/catch` around the send that returns 200 with `{ ok: true, emailSent: false }`; and either a manual resend endpoint or an `activationEmailSentAt` field on `PledgeDoc` so the idempotent path can re-attempt a send it has not yet made. Also pin the variable-name contract (spec §7.2 / O5) with a test, per `p3v2:343`.

## M6 - There is no task that builds the form the family types their account number into

Walk the plan task by task and a family can never submit a pledge. Task 3 is schemas, Task 4 is the server function, Task 6 is routes, Task 9 is the **card** (spec §5.1's four states - the ask, `pending`, `active`, `cancelled`), Task 11 is the export. ## M7 - Task 12 Step 1's route-enumeration test is not implementable as written, and repeats the vacuousness it is fixing

`:388` - `const routes = await globby('src/app/api/**/route.ts');`, then *"hit each with each role, and assert no response body ever contains a bank field name or the seeded account number."*

## M8 - The "safe by construction" enumeration at `:391` is factually wrong

Plan `:391`: *"every `collectionGroup()` in the repo targets only `donations`/`enrollments`/`invites`/`members`; `listCollections()` is never called"*, offered as the basis for the design's headline claim.

`listCollections()` is genuinely never called - verified, zero hits. The `collectionGroup()` enumeration is not:

- **A fifth literal is missing:** `joinRequests`, in three files - `apps/portal/src/features/setu/join-request/get-by-token.ts`, `approve-request.ts`, `decline-request.ts`.
- **Two call sites take the collection-group name from a variable, one of them straight off the query string:**
  - `apps/portal/src/app/api/check-in/teacher/report/route.ts:14,23` - `const classId = url.searchParams.get('classId'); ... portalFirestore().collectionGroup(classId)`
  - `apps/portal/src/app/api/check-in/teacher/uninformed/route.ts:21` - `collectionGroup(c.classId)` over config-driven class ids

A Firestore collection-group query matches **top-level** collections with that id as well as subcollections, so `collectionGroup('pledge_secrets')` would return the top-level `pledge_secrets` docs - the isolation argument in spec §4.2 rule 3 does not hold against a collection-group read.

Not exploitable today: the route is teacher-gated (`can-access-route.ts:30`) and the query adds `.where('classId','==',classId).orderBy('date','desc')`, which no `pledge_secrets` doc (`{pid, encryptedPayload, iv, authTag, keyVersion, createdAt}`) can satisfy. But the plan's stated reason for safety is wrong, and the safety is one added field away from evaporating. That matters because Task 12 is the task whose entire job is to **pin** this.

**Fix.** Correct `:391`. Add to the pin: a test asserting no `collectionGroup` argument is a non-literal (an AST/regex check over `src/`), plus a rule that `pledge_secrets` documents never carry a `date` or `classId` field. State the top-level-match property explicitly so the next reader does not repeat the spec §4.2-rule-3 reasoning.

Make Step 2's named owner a checkbox that blocks the flag flip, not a note.

# MINOR

1. **`cipher.setAuthTag` does not exist.** Task 2 Step 3 `:125` - `// ... setAuthTag read AFTER final()` inside `encryptBankDetails`. On a Cipher the method is `getAuthTag()`; `setAuthTag` is Decipher-only. Verified on Node v24.13.1: `typeof cipher.setAuthTag === 'undefined'`. An executor following the comment literally gets a TypeError. (The **decrypt** order the plan gives - `setAAD` -> `setAuthTag` -> `update` -> `final` - is correct and I ran it: round-trips, and `pid-B` throws `Unsupported state or unable to authenticate data`.)
