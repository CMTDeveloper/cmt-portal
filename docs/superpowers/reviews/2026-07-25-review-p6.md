# Review: P6 - Dormant-Family Skip & Unknown-Centre Prompt
Plan: `docs/superpowers/plans/2026-07-25-launch-p6-migration-dormant-and-centre.md`
Spec: `docs/superpowers/specs/2026-07-24-aug-3-launch-batch-design.md` §1.9a / §1.9b / §1.9c
Reviewed against real code at HEAD `b1395e0`. Only problems listed.

**Verdict: REQUEST CHANGES.** 2 critical, 7 major, 7 minor.
The dormancy predicate itself is sound and its numbers reproduce exactly against
the real snapshot. The two critical defects are on the *centre-prompt* half:
as written it is dead code that ships green tests, and if revived it deadlocks
the family in a redirect loop.

## CRITICAL

### C1 - The flag never reaches the gate; Task 4 ships as dead code with passing tests
**Task 2 Step 3 + Task 4 Step 3.**

**Claim:** "add `locationNeedsConfirmation: z.boolean().nullable().optional()` to
`FamilyDocSchema`" (Task 2 Step 3) is sufficient for the gate to read
`data.family.locationNeedsConfirmation` (Task 4 Step 3).

**Truth:** `FamilyDoc` values reaching the gate are **not produced by
`FamilyDocSchema.parse()`**. `getCurrentFamily()`
(`apps/portal/src/features/setu/members/get-current-family.ts:42`) delegates to
`getFamilyByFid()`, which builds the object with a **hand-written field map**:

`apps/portal/src/features/setu/members/get-family-by-fid.ts:29-45`
```ts
  const family: FamilyDoc = {
    fid: familyData.fid,
    publicFid: familyData.publicFid ?? null,
    ...
    familyAddress: familyData.familyAddress ?? null,
    disclaimersAccepted: ...
  };
```
There is no spread of `familyData`. A field absent from this map is **always
`undefined`** no matter what the Zod schema says. So
`data.family.locationNeedsConfirmation === true` is never true, the gate never
fires, and §1.9c ships doing nothing. The same map feeds `getSessionFamily()`
(`get-session-family.ts:22`), so `GET /api/setu/family` would not return it either.

This will not be caught: Task 4's tests mock `getCurrentFamily` (`mockCurrentFamily({...})`),
so all four assertions pass green against a feature that is inert in UAT and prod.
The file's own comment at `get-family-by-fid.ts:79-82` warns about exactly this
class of omission for `inviteStatus`.

**Fix:** Task 2 must also modify `get-family-by-fid.ts` to add
`locationNeedsConfirmation: familyData.locationNeedsConfirmation ?? null,` to the
hand-map, and add it to the Task 2 `git add` list. Add a `getFamilyByFid` test
(not a mocked-gate test) that round-trips the field from a fake Firestore doc.

### C2 - A family whose ONLY gap is the centre hits an infinite redirect loop
**Task 4 Steps 4-5 (and Step 7's warning misdiagnoses the cause).**

**Claim:** Step 4 - "render a centre selector **only** when the flag is set …
Follow the existing family-level field pattern the form already uses for
`familyAddress`". Step 7 - the bounce-back risk is soft-nav / stale `use cache`.

**Truth:** `complete-profile-form.tsx` **hard-navigates back to `/family` on load**
when it thinks there is nothing to do, and that check has no notion of the centre:

`apps/portal/src/features/setu/members/complete-profile-form.tsx:223-231`
```ts
const scoped = membersRequiringCompletion(result.members, result.currentMid, result.isManager);
const addressDone = !result.isManager || isFamilyAddressComplete(result.family);
if (scoped.every((m) => isMemberComplete(m)) && addressDone) {
  navigateTo('/family');
  return;
}
```
The target family for §1.9c is a *returning* family: members complete, address
complete, only the centre unknown. Flow: gate redirects to `/complete-profile` →
form loads → short-circuit fires → `navigateTo('/family')` (a **hard** nav, so the
gate re-runs server-side on fresh data) → gate fires again → `/complete-profile` →
… A permanent loop, and unlike the stale-cache case the plan describes, a hard
navigation makes it *worse*, not better. Step 7's E2E ("assert no bounce-back
loop") would catch it, but the plan gives the implementer no code change that
prevents it.

Two more places in the same file silently ignore the centre:
- `:288-295` `allReady` = `membersOk && addressReady`. A manager with every member
  complete and a valid address is "all set" without picking a centre - the Save
  button proceeds and the flag is never cleared.
- `:372-391` the manager PATCH sends `{ familyAddress: {...} }` only.

**Fix:** Task 4 must explicitly specify all four edits, not just "render a selector":
1. `:227` extend the short-circuit - `const nothingToConfirm = !result.isManager || result.family.locationNeedsConfirmation !== true;` and AND it into the guard.
2. `:288-295` add `centreReady` to `allReady`.
3. `:377-385` include `location` in the PATCH body when the flag was set.
4. Seed a `centre` state from the loaded family (see M9 - **not** pre-selected).

## MAJOR

### M1 - Task 3 Step 4 is unimplementable as written: the script has no roster rows
**Task 3 Step 4** ("In `migrate-legacy-families.ts`, skip dormant families").

**Claim:** Interfaces - `export function isDormantLegacyFamily(rows: readonly LegacyRosterRow[]): boolean`,
wired into the migration script.

**Truth:** the script never sees a `LegacyRosterRow`.
`apps/portal/scripts/migrate-legacy-families.ts:91`
```ts
let families = await listAllFamilies();
```
`listAllFamilies()` (`apps/portal/src/features/check-in/shared/rtdb/family-lookup.ts:212-230`)
returns the **check-in `Family` type**: `{ fid, name, contacts, paymentStatus, students }`.
It carries **no `center` field at all**, and `level` survives only as
`Student.level`, already normalized lossily at `family-lookup.ts:138-139`:
```ts
const rawLevel = student.level ?? '';
const level = isAdult || rawLevel === 'NULL' ? '' : rawLevel;
```
(adults are blanked, and only the exact string `'NULL'` is - lowercase `'null'`
would survive). Reconstructing dormancy from that shape is impossible for `center`
and unsafe for `level`.

Additionally `LegacyRosterRow` is **not exported** (`legacy-parser.ts:28` -
`interface LegacyRosterRow`, no `export`), so the declared signature cannot be
imported by the script.

**Fix:** name the mechanism in the plan. Cleanest given the existing code: export
`LegacyRosterRow`, and have the parser carry dormancy on its own result -
`fetchLegacyFamilyForMigration()` already loads `/roster` and filters the family's
rows (`legacy-parser.ts:237-239`), so add `dormant: isDormantLegacyFamily(rows)` to
`LegacyFamilyForMigration` alongside Task 1's `locationDefaulted`. Then the script
calls `fetchLegacyFamilyForMigration(legacyFid)` (or `lazyMigrateLegacyFamily`
gains a `skipDormant` option) instead of trying to derive it from the check-in shape.

### M2 - `PATCH /api/setu/family` does not accept `location`; the plan asserts it does
**Task 4 Step 5.**

**Claim:** "The family PATCH accepts `location` and, when it changes, clears
`locationNeedsConfirmation`."

**Truth:** `apps/portal/src/app/api/setu/family/route.ts:28-31`
```ts
const patchSchema = z.object({
  familyEmergencyContact: FamilyEmergencyContactSchema.nullable().optional(),
  familyAddress: FamilyAddressSchema.optional(),
});
```
Zod objects strip unknown keys by default, so a `{ location: 'Scarborough' }` PATCH
parses to `{}`, falls through `:54-56` (no key copied), and hits `:57-59`
→ **400 `bad-request`**. Sent alongside `familyAddress`, `location` is silently
dropped and the family stays Brampton with the flag still set - the "re-divert
forever" case the step itself warns about.

**Fix:** the step must specify the schema addition (`location: z.string().min(1).optional()`),
the `update.location` copy, the explicit `update.locationNeedsConfirmation = false`
(or `FieldValue.delete()`), and validation of the value against
`getLocationOptions()` so a crafted PATCH cannot write an arbitrary centre string
into a field that drives level matching and teacher rosters.

### M4 - The mirrored profile guard at `layout.tsx:76` is not updated
**Task 4 Step 3.**

**Claim:** add the 4th condition "to the manager-scoped condition" at `:53-56`.

**Truth:** the profile-completeness test is deliberately duplicated inside
`DisclaimerGate` so Suspense resolution order cannot decide the destination:

`apps/portal/src/app/family/layout.tsx:76`
```ts
if (incompleteMembers(data.members).length > 0 || !isFamilyAddressComplete(data.family)) return null;
```
Adding a 4th profile condition only at `:53-56` desynchronises the two. A manager
who needs centre confirmation **and** has a stale disclaimer looks "profile
complete" to `DisclaimerGate`, which will `redirect('/acknowledgements')`; whichever
gate throws first wins the race. The comment at `:64-66` states the invariant this
breaks.

**Fix:** mirror the new condition at `:76` in the same step. Note this also
affects **P4** (see M7).

### M5 - `/welcome/roster` will permanently report "299 missing" after the skip
**Task 3 (unlisted consequence).**

**Claim:** "The skipped set is counted in the summary and written to `--csv-out` so
it is auditable, never silent."

**Truth:** the auditability story stops at the CSV. The shipped
migration-completeness check diffs *every* legacy roster fid against Setu:

`apps/portal/src/features/setu/roster/reconcile-migration.ts:24`
```ts
const missingFids = legacyFids.filter((fid) => !setuLegacyFids.has(fid));
```
After the skip, `GET /api/welcome/families/migration-status` reports

"deliberately skipped as dormant" from "the migration broke". That is a red
health indicator on a launch-week screen with no explanation.

**Fix:** either exclude dormant fids from `legacyFids` in `getMigrationStatus` and
report them in a new `skippedDormant` count, or add a runbook line explaining the
expected 299. Add to Task 3's files + `MigrationStatusResponse` changelog if the
shape changes.

### M6 - Skipped families are invisible to welcome-team; §1.9c Part 1 only proves *sign-in* findability
**Task 3 / Self-Review line "§1.9c part 1 findability → no work needed".**

**Claim:** "Nothing is lost … `find-family-by-contact.ts:62-71` falls back to the
legacy roster."

**Truth:** that fallback covers the *family's own* sign-in and the kiosk. Staff-side
lookup has **no** legacy fallback - `searchFamilies` queries only Firestore:
`apps/portal/src/features/setu/search/search-families.ts:62-75` (direct `fid`,
`where('legacyFid','==')`, `searchKeys`, `publicFid`, `publicMid` - all on
`collection('families')`), and `/welcome/roster` browses the same collection
(`build-csv-rows.ts:21`, `report-dataset.ts:41`). So on launch Sunday a welcome-team
member cannot look up any of the 299 by name, phone, or legacy FID at the desk.

**Fix:** state the tradeoff explicitly in the plan and the runbook (this may be
acceptable, but it must be a decision, not a surprise). If not acceptable, the
skip needs a staff-visible fallback or the families need a lighter-weight
"stub" migration.

### M8 - The centre selector's default value is unspecified - the likely default defeats the whole feature
**Task 4 Step 4.**

**Claim:** "Follow the existing family-level field pattern the form already uses for
`familyAddress` and `ProvinceSelect`."

**Truth:** that pattern **seeds from the stored value**
(`complete-profile-form.tsx:238-243`, e.g. `setProvince(addr?.province ?? 'ON')`).
Applied here it seeds the selector with `family.location` - which for every flagged
family is the **defaulted `'Brampton'`**. The family clicks "Save and continue"
without touching it, the flag clears, and they are silently confirmed as Brampton:
precisely the outcome §1.9c exists to prevent, now with a false audit trail saying
they chose it.

**Fix:** specify that the selector renders **unselected** (`value=''` +
`<option value="" disabled>Select your centre…</option>`) and that `centreReady`
requires a non-empty explicit choice.

## Answers to the specific questions asked

**2. The dormancy predicate - verified against `apps/portal/.rtdb-snapshot/roster.json`
(2,543 rows, 867 families).**
- **(a) Field names correct.** `center` and `level` are present on **all 2,543 rows**
  (every row carries the full 25-key schema). No `centre` spelling variant.
- **(b) `"NULL"` handling correct.** `absent()` (`''` / case-insensitive `NULL`)
  matches the parser's existing `clean()` semantics (`legacy-parser.ts:95-101`).
  Observed `center` values are exactly `Brampton 1411, Scarborough 548, "NULL" 574,
  "ALL" 10` - no lowercase `null`, no empty strings. `level`: `"NULL"` on 1,708 rows,
  a real level on 835.
- **(c) It cannot skip a family with an ACTIVE child.** Any real `level` on **any**
  row disqualifies the family. Reproduced the plan's figures **exactly**:
  **299 dormant / 867**, **124** with ≥1 child row (205 child rows), **119** families /
  **190** children with a mappable `schoolGrade`. Cross-checks on all 299: `payment`
  is `Unpaid` on every one of their 574 rows, and **zero** have a non-NULL `classid`
  or `classyear`. The only caveat is m4 (68 have a 2025/2026 join date).
  **The predicate is correct.** The risk in this plan is not the predicate.

**3. `locationNeedsConfirmation` necessity and safety.** `FamilyDocSchema.location`
really is `z.string().min(1)` at `packages/shared-domain/src/setu/schemas/family.ts:55`
- non-nullable, non-optional - so the additive-flag approach **is** necessary.
`nullable().optional()` does not break existing reads (`FamilyDocSchema` is a plain
`z.object`, unknown keys stripped, missing optionals fine; siblings `publicFid`,
`familyAddress`, `disclaimersAccepted` use the identical pattern). **But the schema
is not the read path** - see **C1**.

**4. The gate change.** `=== true` handles `undefined` and `null` correctly, and
**no existing family would be diverted** - doubly so, because `getFamilyByFid`'s
hand-map never populates the field at all (C1). The ~867-family mass-divert risk the
plan is most worried about is not present. The real gate risks are M4 (`:76` mirror)
and C2 (the loop).

**5. The centre selector.** The form **can** render a family-level field - it already
does for the home address (`complete-profile-form.tsx:687-741` renders it once,
manager-only, outside the member cards; `:372-391` PATCHes it after the member loop;
`:274-282` gates submit on it). `/api/setu/locations` **is** reachable by a family
role: it is in `PUBLIC_ROUTES` (`packages/shared-domain/src/auth/public-routes.ts:54`)
**and** allowed for `isSetuFamily` in `canAccessRoute`
(`packages/shared-domain/src/auth/can-access-route.ts:194-207`) - the plan's claim is
correct in substance. The gaps are C2 (three unaddressed call sites) and M8 (default value).

**6. Does the family PATCH accept `location`?** **No.** See **M2** - the schema
(`route.ts:28-31`) has only `familyEmergencyContact` and `familyAddress`; a
`location`-only PATCH 400s and a combined one silently drops it. Clearing the flag
is likewise unimplemented and unspecified.

**7. P4 interaction.** Both plans edit `family/layout.tsx` at **non-overlapping
hunks**, so git merges cleanly. The conflicts are semantic (M7): P4 clones the
`:76` guard P6 fails to update (M4), both edit
`apps/portal/src/app/family/__tests__/layout.test.tsx`, and both declare themselves
independent.

## Positive observations
- The dormancy predicate is genuinely correct and its measurements reproduce to the
  digit against real data - rare, and the "literal `NULL` is a string" regression test
  (Task 3 Step 1, last case) encodes a real prior mistake.
- Choosing an additive `nullable().optional()` flag over nulling `location` is exactly
  right and correctly reasons about read-time doc validation.
- Task 4 Step 1's fourth test ("does not divert a family that never had the flag") is
  the right instinct for the highest-blast-radius failure.
- Skipping rather than deleting, with lazy migration as the recovery path, is the
  right shape and consistent with the 2026-07-20 rollover decision.
- Conditional spread over writing `false`, justified by `exactOptionalPropertyTypes`,
  matches the repo's actual tsconfig posture.
