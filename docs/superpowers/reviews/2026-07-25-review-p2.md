## CRITICAL

### C1 - Task 2 Step 5: the backfill computes the WRONG Sunday (off by up to 7 days)

- **Claim:** "It sets `sessionDate = mostRecentSunday(new Date(date))` for every doc missing it."
- **Truth:** `mostRecentSunday(now: Date)` (`apps/portal/src/features/setu/calendar/calendar.ts:40-45`)
  first converts `now` to a **Toronto** calendar date via `torontoToday()`
  (`calendar.ts:30-37`, `timeZone: 'America/Toronto'`). `new Date('2026-09-06')` is parsed as
  **UTC midnight**, which is `2026-09-05 20:00` in Toronto (EDT). So:
  - `torontoToday()` -> `'2026-09-05'` (Saturday)
  - `mostRecentSunday()` -> `'2026-08-30'`

  A guest doc stamped `date: '2026-09-06'` (a real Sunday) gets `sessionDate: '2026-08-30'` -
  **a full week early**. Every backfilled doc lands on the wrong Sunday and stays invisible to
  teachers, which is the exact bug the task exists to fix. Worse, this is a one-shot write against
  UAT (and eventually prod) data, and the task's own idempotence rule ("skip docs that already have
  the field") means a re-run will **not** repair it.
- **Fix:** anchor at noon UTC the way the rest of the repo does
  (`attendance-marker.tsx:29-33`, `calendar.ts:42` both use a `T12:00:00Z` anchor):
  ```ts
  const sessionDate = mostRecentSunday(new Date(`${date}T12:00:00Z`));
  ```
  Add a unit test over the backfill's date mapper asserting Sunday -> itself
  (`'2026-09-06'` -> `'2026-09-06'`) and Wednesday -> preceding Sunday
  (`'2026-09-09'` -> `'2026-09-06'`). Make the script re-runnable with a `--force` (or
  `--recompute`) flag so a bad run is recoverable.

### C2 - Task 2 Step 4: swapping `date` for `sessionDate` breaks every non-Sunday query, and the caller is never updated

- **Claim:** Files list for Task 2 is only `guest-check-ins.ts` + `check-in-attendance.ts`.
  Step 4: "`readPortalGuestChildren` filters on `sessionDate` instead of `date`... Rename the
  parameter to `sessionDate` for clarity."
- **Truth:** the sole caller is `getLevelVisitorsView`
  (`apps/portal/src/features/setu/teacher/visitors.ts:59-63`), which passes its own `date`
  parameter straight through to **both** `readDoorGuestCheckIns(date)` and
  `readPortalGuestChildren(date)`. That `date` comes from a **user-supplied, unnormalized**
  `?date=` param validated only by `/^\d{4}-\d{2}-\d{2}$/`
  (`app/teacher/levels/[levelId]/visitors/page.tsx:26`).

  After the change, `sessionDate` is *always* a Sunday in the stored docs. So for any non-Sunday
  `?date=`, the query `where('sessionDate','==', '2026-09-09')` matches **nothing** - where today
  it correctly returns that Wednesday's guests via `date`. The plan trades "midweek guests are
  invisible on the Sunday view" for "midweek guests are invisible on the midweek view", and never
  touches `visitors.ts`. Task 2 Step 7 even runs the `visitors` tests, implying awareness, but no
  edit is specified.
- **Fix:** normalize at the call site and make it explicit. In `visitors.ts`:
  ```ts
  readPortalGuestChildren(mostRecentSunday(new Date(`${date}T12:00:00Z`)))
  ```
  Add `apps/portal/src/features/setu/teacher/visitors.ts` to Task 2's Files list, and add a test
  that `getLevelVisitorsView(levelId, '2026-09-09')` still surfaces a guest whose
  `sessionDate` is `'2026-09-06'`. (Alternatively export a single shared
  `sessionDateFor(ymd: string)` helper and use it in the writer, the reader's caller, and the
  backfill - one function, three call sites, no third drift.)

## MAJOR

### M1 - Task 3: three unfiltered `collectionGroup` scans on the eager render; donations is read TWICE per request

- **Claim (Step 3 docstring):** "One unfiltered collectionGroup read per concern... the same
  index-free pattern `roster-confirmation.ts` uses."
- **Truth:** the comparison is wrong in both directions.
  1. **`deriveRoster` already reads `collectionGroup('donations').get()`** in the same request,
     via `deriveConfirmedFidsForLevel` (`roster-confirmation.ts:73`), which
     `getLevelAttendanceView` calls with `{ withConfirmation: true }`
     (`level-attendance-view.ts:52`). Task 3 adds a **second, identical** full-collection donations
     scan to the very same page load.
  2. **`grade-eligible.ts` is the actual precedent for the unfiltered `collectionGroup('members')`
     scan - and it is deliberately LAZY.** Its own docstring
     (`grade-eligible.ts:52-57`) says "Lazy - only fetched when a teacher expands the section -
     because it is an intentionally broad scan (all members at a location)". Task 3 moves that same
     ~2,500-doc scan onto the **eager** path. A teacher who then expands "Not in this class yet"
     pays it twice.
  3. **`deriveRoster` deliberately does NOT fan out or scan** - it does a batched
     `db.getAll(...)` of *exactly* the enrolled member docs, with a long comment explaining why
     (`roster.ts:156-174`). Task 3's approach is the opposite of the pattern it claims to follow.
- **Scale (spec §1.8 measured numbers):** ~867 families / 2,543 roster rows. Per attendance
  render Task 3 adds roughly `2,500 members + ~870 active enrollments + N donations` document
  reads - and `donations` grows monotonically forever. This route is hit by every teacher, on every
  level, every Sunday morning, plus again through `GET /api/setu/teacher/levels/[levelId]/roster`
  (`route.ts:24`).
- **Why the anti-fan-out rule does not apply here:** the rule exists because a **per-family loop
  over the whole roster** (769 families) times out. But `buildAttendanceDetailIndex` is called with
  the **level-scoped** fid set - one class, typically 20-40 families. `student-detail.ts:62` already
  reads one family's members subcollection directly for exactly this data (manager contacts).
  30 parallel subcollection gets is not the 769-family fan-out the rule targets.
- **Fix (pick one, in order of preference):**
  - **Reuse what `deriveRoster` already has.** It holds `enrMetaByFid` (eid/oid/enrolledMids per
    fid) and the donations snapshot is already read one frame later. Thread the payment inputs out
    of `deriveRoster`/`deriveConfirmedFidsForLevel` instead of re-reading. Zero new reads.
  - For contacts, do a bounded parallel read of `families/{fid}/members` for the level's fids
    (same shape as `student-detail.ts:62`), guarded by a cap + comment stating the fid set is
    level-scoped, not roster-scoped.
  - At minimum: pass the already-fetched donations snapshot into `buildAttendanceDetailIndex`
    rather than re-querying it.

### M2 - Task 3: `expected` is computed differently from every other payment surface

- **Claim (Step 3):** `const amount = e.suggestedAmountOverride ?? e.suggestedAmountSnapshot ?? 0;`
- **Truth:** every other payment surface resolves the **live** offering amount, not the snapshot:
  - `build-csv-rows.ts:113-117`: `a.override ?? (off ? resolveSuggestedAmount(off, a.enrolledAt) : a.snapshot)` after a batched `getAll` of offerings (`:85-90`)
  - `report-dataset.ts` does the same
  - `payment.ts:24` (`deriveFamilyPayment`) sums `e.effectiveSuggestedAmount`

  So when an offering's pricing tier changes after enrollment, the teacher's Donation Status chip
  will disagree with the welcome roster's payment chip for the same family. That is precisely the
  "same family, three screens, two answers" failure Task 1's own commit message calls out.
- **Fix:** reuse `resolveSuggestedAmount(offering, enrolledAt)` with a batched `getAll` of the
  level's offerings (there is typically exactly one `oid` per level, so this is a single doc read -
  cheaper than the collectionGroup scan it replaces). Add a test where
  `suggestedAmountSnapshot !== resolveSuggestedAmount(...)` and assert the chip matches the roster.

### M3 - Task 4: `safetyNotes` cannot be populated from the files the task lists

- **Claim:** Files = `level-attendance-view.ts:7-17` + its test. `AttendanceViewRow` gains
  `safetyNotes: string | null`.

  and then discarded. `RosterMemberInput.foodAllergies` exists (`roster.ts:12`) but never reaches
  `RosterMember`. The task as written cannot produce a non-null `safetyNotes`.
- **Fix:** add `apps/portal/src/features/setu/teacher/roster.ts` to Task 4's Files list - widen
  `RosterMember` with `foodAllergies: string | null` and carry it through `buildRoster` (keep
  `hasSafetyInfo` as the derived boolean so nothing downstream breaks). Update `roster.test.ts`.
  Note the privacy delta explicitly: allergy free-text now ships to the client for **every**
  student on the level, where today only a boolean does (spec §4.6 covers contact + donation, not
  medical text).

### M5 - Task 5: the tests reference an `onMark` prop that does not exist

- **Claim:** `render(<AttendanceMarker rows={ROWS} onMark={onMark} />)`;
  `expect(onMark).toHaveBeenCalledWith('CMT-A-03', expect.anything())`.
- **Truth:** `AttendanceMarker` has no `onMark` prop

### M6 - Task 5: `getAllByRole('button', { name: /mark/i })[0]` does not select a student row

- **Claim:** "await userEvent.click(screen.getAllByRole('button', { name: /mark/i })[0]!)"
- **Truth:** in DOM order, `/mark/i` matches, before any row:
  - the `Unmarked {n}` filter pill (`:486-488`)
  - the `Mark all present` / `Clear all` button (`:490-496`)

  So `[0]` is a filter pill. And the row `aria-label`s are
  `"${first} ${last}... - present"` or `"... - not marked"` (`:516`), so the *present* row
  (`CMT-A-03`, the one the assertion targets) does **not** match `/mark/i` at all. The test is
  wrong three ways.
- **Fix:** follow the existing `row(name)` helper convention
  (`__tests__/attendance-marker.test.tsx:27-29`) - select by student name, then use
  `within(row).getByRole('button', ...)` for the toggle.

### M7 - Task 5 / Task 8: `getByText` / `getByLabelText` will throw - both branches render in jsdom

- **Claim:** Task 5 `expect(screen.getByText('Vaibhav Rana'))...`;
  Task 8 `screen.getByLabelText(/payment/i)`, `screen.getByPlaceholderText(/search/i)`.
- **Truth:** the plan's own Task 5 Step 3 specifies a desktop table **plus** an
  `md:hidden` mobile card list "from the same row data". jsdom does not apply media queries, so
  **both branches render and every element appears twice**. The repo has already been bitten by
  this and documents it verbatim:
  - `features/setu/roster/__tests__/roster-browser.test.tsx:49-53`: "RosterBrowser renders BOTH a
    mobile (`block md:hidden`) and a desktop (`hidden md:block`) branch - CSS media queries don't
    apply in jsdom, so every element appears twice AND each branch owns independent React state.
    We use `getAllBy*`/`findAllBy*` + `.length` (repo convention), and for interaction tests we act
    on EVERY matching control so both branches move together."
  - `features/setu/reports/__tests__/reports-hub.test.tsx:54` says the same.

  `getBy*` throws on multiple matches, so as written both test suites fail. Task 8 is worse: each
  branch owns **independent state**, so clicking one Reset leaves the other branch's filters set,
  and the assertions must cover both (see `clearDefaultFilters()` at `roster-browser.test.tsx:55-60`).
- **Fix:** use `getAllBy*` + iterate, per the documented convention.

### M8 - Task 5 will silently break the entire existing `attendance-marker.test.tsx` suite

- **Claim:** Step 2 "Expected: FAIL - no contact rendered, no link."

  `getByRole('button')` to the new row structure; the toggle keeps `aria-pressed` and an
