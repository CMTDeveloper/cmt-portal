## CRITICAL

### C1 - No task implements the `enroll-family.ts` change the whole plan depends on
**Where:** File Structure line 25 vs. Tasks 1-7; Task 5 Step 3.
**Claim:** "`enroll-family.ts` - accept an override and explicit mids".
**Truth:** Zero task steps modify that file. Reality today:
- `enroll-family.ts:8-13` — `EnrollFamilyParams` is only `{ fid, oid, enrolledVia, enrolledByMid }`. No mids, no override, no membershipMode.
- `enroll-family.ts:124-131` — `enrolledMids` is derived from `memberEligibleForProgram`. For `eligibility.memberType: 'adult'` (`program.ts:80`) that matches **every** Adult, including teacher-assigned adults and `inviteStatus:'pending'` invitees — precisely the two sets Task 3 exists to exclude.
- `enroll-family.ts:153` — `suggestedAmountOverride: null` is hardcoded.
- Nothing writes `membershipMode` anywhere.

So Task 5 Step 3 as written produces: all adults enrolled, `override: null`
($101 billed to a BV family), `membershipMode` absent → treated as `'auto'` →
**Task 2 becomes dead code and the selection is overwritten on the next member
edit — the exact B2 failure the plan says it prevents.** Task 5's own tests 3
and 4 cannot pass.

**Fix:** Add an explicit task between Task 2 and Task 5 that extends
`EnrollFamilyParams` with `enrolledMids?: string[]`,
`suggestedAmountOverride?: number | null`, `membershipMode?: 'auto' | 'manual'`,
threads them into the `txn.set` at `enroll-family.ts:139-157`, and applies the
`no-eligible-members` guard (`:135-137`) to the **supplied** list. Keep the
default path byte-identical for existing callers.

### C2 - `enrollFamily`'s already-active branch is a strict no-op → permanent redirect loop
**Where:** Task 4 test 7 + Task 5 Step 3.
**Claim:** Task 4 test 7 requires the gate to fire *again* when the adult-class
enrollment exists with `enrolledMids: []` (spec §2.1 cond. 4, §4.5 row 3).
**Truth:** `enroll-family.ts:108-113`:
```ts
if (enrollmentSnap.exists) {
  const existing = enrollmentSnap.data() as { status: string; suggestedAmountSnapshot: number };
  if (existing.status === 'active') {
    return { created: false as const, eid, suggestedAmountSnapshot: existing.suggestedAmountSnapshot };
  }
}
```
`eid` is deterministic (`${fid}-${oid}`, `:40`), so the re-selection hits the
existing active doc and **writes nothing**. Sequence: selected parent leaves →
Task 2's prune sets `enrolledMids: []` → gate fires → `/adult-class` → family
picks someone → POST 200 → nothing written → gate fires again. **The manager
can never reach `/family` again.** Same trap on any future "change which parent"
re-submit.

**Fix:** The adult-class route must reconcile an existing active enrollment
(update `enrolledMids` / `membershipMode` / override in place), not go through
the create-only path. Add a test that POSTs twice with different mids and
asserts the second write lands.

### C3 - The gate has no feature flag and no "an open offering exists" precondition
**Where:** Task 6 Step 3; Task 4 Step 3; Task 7 Step 2.
**Claim:** "Add `AdultClassGate` after `DisclaimerGate` … then `redirect('/adult-class')`."
**Truth:**
1. `DisclaimerGate` is flag-gated (`layout.tsx:68` → `flags.setuDisclaimers`,
   `flags.ts:33` "ships dark; flip on at launch"). Task 6 adds the new gate
   unconditionally. That violates CLAUDE.md discipline 5 ("All risky features
   gated through `flags.ts`. No hardcoded booleans") and removes the kill switch
   3 days before an Aug-3 launch.
2. Spec §2.1's five conditions — which Task 4 Step 3 says to implement verbatim
   — never check that a current adult-study-class offering is **reachable**.
   `get-open-offerings.ts:60-68` filters `enabled === true` and
   `endDate == null || endDate >= now`, and
   `getOpenOfferingsForFamily` scopes to the family's `location`.

Consequence: the day the launch offering expires, or the day someone toggles
`enabled` off, or if Task 7 Step 2 misses one location, **every paid BV manager
at that location is redirected to `/adult-class`, cannot enroll, and cannot
reach `/family` at all.** There is no escape hatch in the design.

**Fix:** Add `flags.setuAdultClass` (default off) gating both the gate and the
route, and add condition 0 to `needsAdultClassSelection`: resolve the open
offering first via `getOpenOfferingsForFamily('adult-study-class', family.location)`
and return `false` when there is none. Test both.

## MAJOR

### M1 - The plan never closes the $101 door on Bala Vihar families
**Where:** Task 7 Step 1 (`status: 'active'`) vs. the canonical fee rule (spec §4.2).
**Truth:** An `active` program shows on the generic enroll surface, and
`apps/portal/src/app/api/setu/enrollments/route.ts:56-60` calls the *same*
`enrollFamily` with `enrolledVia: 'family-initiated'` — which always writes
`suggestedAmountOverride: null` (`enroll-family.ts:153`). A BV family who
enrolls through `/family/enroll/adult-study-class` therefore gets billed **$101**
and has **all** adults auto-enrolled; the gate then never fires, because
condition 4 is satisfied by a non-empty `enrolledMids`. Two doors to one
program and the more discoverable one bills the family the spec says pays
nothing. Spec §4.5 row 1 covers "adult class *first*, BV later" — this is the
different and more likely case of a BV family using the normal enroll page.
**Fix:** Either apply the BV waiver inside the generic enroll route for
`adult-study-class`, or hide the program from the generic enroll surface. Add a
test: "BV family enrolls via `POST /api/setu/enrollments` → override 0".

### M2 - Spec §6 item 5 (roster payment) has no task, and a 0 expected total reads `unknown`
**Where:** Self-Review "§6 verification 1-7 → Tasks 1-7 ✅".
**Truth:** `roster/payment.ts:7-10`:
```ts
export function paymentFromAmounts(activeCount: number, expected: number, paid: number): RosterPayment {
  if (activeCount === 0 || expected <= 0) return 'unknown';
  return paid >= expected ? 'paid' : 'outstanding';
}
```
Traced:
- **BV(500) + ASC(0) → expected 500 → `paid`.** ✅ The case the spec asserts is safe.
- **BV cancelled after the waiver** (spec §4.5 row 2 *explicitly* keeps `override: 0`) → the only active enrollment is ASC at 0 → `expected === 0` → **`'unknown'`, not `paid`** — on `/welcome/roster` (`deriveFamilyPayment`, `payment.ts:20-29`), in `deriveFamilyRosterSignals` (`family-engagement.ts:46,50`) and in the CSV (`build-csv-rows.ts:113-118`). Same for a BV family on a teacher-managed / empty-`pricingTiers` offering.
- **ASC first, BV later** → expected 601, paid 500 → `outstanding`. Spec §4.5 accepts this (O3) but the spec's "B3 dissolves" table doesn't list it.
The `?? 0` reads in `payment.ts:24` / `family-engagement.ts:46` and the
`typeof === 'number'` reads in `report-dataset.ts:95` / `build-csv-rows.ts:66`
all preserve a literal `0` correctly — the problem is not truthiness, it is the
`expected <= 0` classifier.
**Fix:** Add a task covering spec §6 item 5 across `deriveFamilyPayment`,
`deriveFamilyRosterSignals` and `buildRosterCsvRows` with a 2-enrollment
fixture, and decide explicitly whether `expected === 0` should classify as
`paid` rather than `unknown`.

### M3 - `/adult-class` is missing from middleware's `isSetuRoute` list
**Where:** Task 5 Step 4 (only `canAccessRoute`); `middleware.ts` absent from File Structure.
**Truth:** `apps/portal/src/middleware.ts` `deny()` builds `isSetuRoute` from an
explicit path list that includes `/complete-profile` and `/acknowledgements` —
the two routes P4 is modelled on. `/adult-class` is not in it, so an
expired-session or wrong-role manager hitting `/adult-class` is redirected to
the **legacy `/login`**, not `/sign-in`. (`AUTH_ENTRY_ROUTES` /
`dashboardForRole` are fine — `/adult-class` is not an entry route and
`dashboardForRole` only maps family roles to `/family`; no bad interaction there.)
**Fix:** Add `/adult-class` to the `isSetuRoute` disjunction plus a middleware
test, and list `apps/portal/src/middleware.ts` in Task 5's Files.

### M5 - Gate condition 3 ("the BV donation is paid") is never defined, and the obvious helpers disagree
**Where:** Task 4 Step 3 ("Implement the five conditions from spec §2.1 in order")
and its undefined fixtures `seedPaidBvFamily` / `seedUnpaidBvFamily`.
**Truth:** `enrollment-confirmation.ts:34` — `isEnrollmentConfirmed` returns
`true` for any `enrolledVia === 'family-initiated'` **regardless of payment**.
An implementer reaching for the repo's "Enrolled" signal would gate families who
clicked Enroll and never paid, contradicting spec §2 ("**After** the BV
donation"). Reaching for a donations sum instead misses legacy-paid
(`getLegacyPaymentStatus`) and teacher-managed offerings
(`paymentSourceOf(...) === 'teacher-managed'` — those families never pay in-portal
and would be gated forever).
**Fix:** Name the predicate in the plan: completed donations with
`d.eid === bv.eid` summing to ≥ `bv.effectiveSuggestedAmount`, **or** `legacyPaid`,
**or** `teacherManaged`. One test per branch.

### M6 - Deferring to `DisclaimerGate` is not "exactly as `layout.tsx:76`"
**Where:** Task 6 Step 3.
**Claim:** "guarding on both earlier gates exactly as `DisclaimerGate` already
guards on profile completeness (`layout.tsx:76`)".
**Truth:** `layout.tsx:76` is a pure in-memory check
(`incompleteMembers(...)` + `isFamilyAddressComplete(...)`). A **fourth** gate
must additionally defer to the disclaimer gate, which needs
`getDisclaimerStateForFamily(portalFirestore(), data.family)` (`layout.tsx:78`)
— an extra Firestore read on **every** `/family/*` render — and must respect the
`flags.setuDisclaimers` short-circuit (`layout.tsx:68`): when disclaimers are
OFF, `DisclaimerGate` never fires and the deferral must not block. Task 6's
one-sentence Step 3 covers none of this, yet its Step 1 test
(`expect(await AdultClassGate()).toBeNull()` for unaccepted disclaimers)
requires it.
Also note `layout.tsx:76` uses `incompleteMembers(data.members)` (all members)
while `ProfileCompletionGate` uses the narrower
`membersRequiringCompletion(...)` scope (`layout.tsx:52`) — copying :76 inherits
that mismatch.
**Fix:** Spell out the deferral explicitly, or extract a shared
`earlierGatesPending(data)` helper that both `DisclaimerGate` and
`AdultClassGate` call.

### M7 - The plan drops spec §4.3's placement and skip path, and will hijack the P5 pledge ask
**Where:** Self-Review "§4.3 → Task 5 ✅".
**Truth:** Spec §4.3 places the ask **on the donation success page**, ordered
*before* the monthly-pledge ask, and requires: "A family who skips the selection
must be able to return to it, via the same state-driven card treatment the
pledge uses, surfaced on the family dashboard." The plan implements a hard
redirect gate only — no success-page ask, no skip, no dashboard card.
Worse: `apps/portal/src/app/family/donate/success/page.tsx` is **inside** the
`/family` layout, so once the BV donation reads paid the new gate redirects away
from it. P5's task `Modify: apps/portal/src/app/family/donate/success/page.tsx`
adds the pledge card to that exact file — **it will never render for a gated
family.** Spec §4.3's own note ("the order matters … adult-class first, pledge
second") is silently unimplementable under this design.
**Fix:** Reconcile spec §2 (gate) with §4.3 (success-page ask + skip) explicitly
in the plan, and either exempt `/family/donate/success` from `AdultClassGate` or
move the ask onto that page and keep the gate as the persistent fallback.
